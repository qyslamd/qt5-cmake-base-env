## 1. SIGTERM 杀不掉应用

**现象**：在 WSL 里以 `timeout 10 <AppImage>` 启动，超时后进程仍存活——
实测有一个实例残留 5 分 54 秒，并在 WSLg 桌面上留下了无法操作的窗口。

**影响**：用户 Ctrl+C、服务停止、CI 结束作业时进程不会退出。

**待分辨的两种可能**（需分别验证，不要直接猜）：

1. AppImage 的 `AppRun` 包装没有把 SIGTERM 转发给子进程
2. `GlobalExceptionHandler` 的信号处理没有真正终止进程

**线索**：`src/core/crashhandler/global_exception_handler.*`；职责划分见
`plan总结.md`
里归档的 D6——GEH 的职责包含 SIGINT/SIGTERM，即这是**声称已覆盖但实际未
验证**的能力。

**入手点**：先补一个子进程测试区分上述两种可能——现有
`tests/core/crashhandler_test.cpp` 的"父进程拉起子进程"骨架可直接复用。

## 2. GEH 与 SingleInstance 无测试

**现状**：两个模块都没有任何测试覆盖。

- `GlobalExceptionHandler`：Qt 消息重定向、SIGINT/SIGTERM
- `SingleInstance`：第二实例转发参数并激活首实例窗口（非 Windows 走
  `showApplication` 信号那条路径，实现见 `main.cpp` 的 `AttachHostFeatures`）

**已有旁证**：进程被 SIGTERM 杀掉后，单实例痕迹（QLocalServer 套接字、
QSharedMemory 段）会残留，导致下一次启动静默转发参数并以 0 退出——日志
为空，因为它退在 `Logger::init()` 之前（与 `main.cpp` 文件头写的启动顺序
一致）。这条旁证同时指向第 1 条。

**入手点**：第二实例的行为可以用现有子进程骨架测：父进程起首实例 → 再起
一个 → 断言第一个收到激活请求且第二个以 0 退出。

## 3. 崩溃栈符号链路无测试

**现状**：符号归档的两条通道都已就绪，但没有测试锁住"事后能解析出调用栈"
这条链：

- Windows：`make_symbols` 目标归档 exe + PDB
- Linux：`make_appimage` 归档未 strip 的可执行文件到 `dist/symbols/`

**已验证到哪一步**：Linux 侧实测归档 25.8 MB / 3579 个符号 / 带调试信息，
而 AppImage 内是 0.96 MB / stripped / 0 个符号，两者对照成立。但**没有人真的
拿崩溃日志里的地址跑过一次 `addr2line`**，Windows 侧也没有解析过 minidump。

**入手点**：在崩溃子进程测试里，从生成的崩溃日志中取一个地址交给
`addr2line -e <归档二进制>`，断言解析出的符号名非空；Windows 侧对应的是用
归档的 exe + PDB 解析 minidump。

## 4. gallery 空载 CPU 偏高（已随 gallery 迁出）

**实测**：gallery 空载稳态 **2.719 CPU-秒 / 8 秒**，对照程序 `demo_app` 为
0.625。插桩已证明**与进度条定时器无关**（进度条所在页未显示时零定时器启动），
来源未查。

**状态**：**已关闭，不再追查。** 该示例先随 `src/libui` 一并迁至独立仓库
`qt-libui`（成为其 `examples/gallery`），随后整个 `qt-libui` 也已从本仓移除
（submodule 解绑，见 `plan总结.md`）——测量对象在本仓已不存在。若日后仍
要追查，需到 `qt-libui` 仓复现；届时注意它已不用 spdlog/日志面板，改用纯 Qt
的 `qInstallMessageHandler` 面板，`LogOutputPanel` 这个可疑项已不存在。

**原本的入手点**（供在 qt-libui 仓复现时参考）：gallery 侧独有而 `demo_app`
没有的部分——gallery 用 `QTabWidget` + `QSplitter` + 日志面板，而 `demo_app`
另有 `mainwindow` 骨架；从两者的差异逐个排除。WSL 下的测量方式：进程启动
4 秒后再取 `TotalProcessorTime` 的 8 秒增量（含启动开销的话差值会被淹没）。

## 6. guidance 库的告警通道：`qWarning` 还是 `Logger` 宏

**现状**：`guidance_bridge.cpp:128`、`guidance_config.cpp:12/16/39/43`、
`guidance_controller.cpp:98/105/122/131`、`guidance_style.cpp:46` 共 9 处用
`qWarning()`，而项目规则要求尽可能走封装的 `Logger` 宏。

**卡在哪**：`src/guidance` 的依赖只有 `Qt5::Gui/Widgets/Core`——它**不链
core**，而且是刻意的（库可整包拷到别的工程用，见 CHANGELOG 的"让 guidance
可当库拷贝"）。要用 `LOG_*` 就得把 core 拖进来，会破坏这个卖点。两条路：

1. 链 core 换 Logger 宏：统一日志，代价是库不再零依赖
2. 保留 `qWarning`：把"为什么不链 core"写成注释，免得下次又被当缺陷报一遍

**来源**：原 `引入的guidance的bug记录.md` 的"附：两处规范问题"（另一条
`#pragma once` 已修）。
