# 崩溃报告回传链路设计

## 一、问题陈述

程序发布给**离线客户**。崩溃后需要客户把崩溃文件发回来，开发者在自己的机器上
恢复崩溃时刻的堆栈，快速定位。

现状（`APP_ENABLE_CRASHPAD=ON`，两平台默认）：

| 环节 | 现状 |
|------|------|
| 捕获 | 已完成。crashpad_handler 随包分发，dump 落在本地数据库 |
| 归档 | 已完成。`dist/symbols/<版本>-<git hash>-<架构>/` 一一对应 |
| **回传** | **断了**：dump 躺在客户的 `%LOCALAPPDATA%` / `~/.local/share` 里，客户不会去找，也不会发 |
| 定位 | Windows 可用归档 PDB；Linux 需未 strip 的 ELF |

崩溃那一刻进程正在死亡（crashpad 模式下没有弹窗机会），所以"告知客户"这件事
只能在**下次启动**做。

### 已确认的能力边界（源码实证，不再重复讨论）

- crashpad 固定写 `MiniDumpNormal`（`minidump/minidump_file_writer.cc:51`），
  **没有** DataSegs / FullMemory → 全局变量与堆对象内容不在 dump 里。
- extra memory ranges 仅 Windows 有效（`crashpad_info.h:76` 明说；
  `ModuleSnapshotElf::ExtraMemoryRanges()` 返回空集）；indirectly-referenced
  memory 的实现在 `snapshot/win/`，Linux 只读选项不采集。
- handler 级注解确实写进 dump，但落在 CrashpadInfo 扩展流里
  （`handler/linux/crash_report_exception_handler.cc:175` →
  `minidump/minidump_crashpad_info_writer.cc:54`），**cdb / WinDbg 看不见**，
  本仓也没有 vendor `tool/` 下的查看器。所以注解的可读副本走 `summary.txt`，
  dump 里那份只作留档。
- 结论：本设计**不追求**"看堆/全局变量"，只保证"栈 + 寄存器 + 模块 + 注解"
  到位。**RelWithDebInfo 下被优化掉的局部变量看不到是预期内的。**

## 二、目标与非目标

**目标**

1. 客户无需任何配置、无需管理员权限，就能拿到一个可以发给开发者的文件。
2. 开发者拿到文件后，用归档符号恢复"哪个函数、哪一行、什么参数"。
3. 崩溃报告能自证"我是哪个构建"（版本 + git hash）。

**非目标**

- 不做自动上传（客户不联网）。上传保持关闭。
- 不做堆/全局变量（见上）。
- 不做崩溃时刻的弹窗（进程正在死，不可靠）。
- 自研模式（`APP_ENABLE_CRASHPAD=OFF`）本期不实现导出，见决策 D4。

## 三、方案

### 3.1 核心能力（`src/core/crashhandler/`）

**全部做成"参数给全"的纯函数**，数据库目录、导出目录、应用元信息都由调用方传入
——这样单元测试可以指向临时目录，不会碰到开发者本机的真实崩溃库；应用侧再包一层
便捷函数。命名按 CLAUDE.md 的函数命名规则用 PascalCase。

```cpp
namespace crash {

// 应用元信息：随 dump 的注解走，也写进 summary.txt
struct AppInfo {
  QString name;          // CRASHPAD product
  QString version;       // 形如 V0.1.0.123
  QString git_commit;    // 归档目录名里的那个短 hash
  QString build_config;  // Debug / RelWithDebInfo ...
};

// 本应用实际使用的崩溃数据库目录（与 crash::Init 用的是同一个）
QString DatabaseDir();

// 启动时记录的应用元信息
const AppInfo& CurrentAppInfo();

// 待处理报告数；打不开库返回 -1（首次运行没有库是正常状态）
int CountPendingReports(const QString& db_dir);

struct ExportResult {
  int exported = 0;      // 成功导出的报告数
  QString target_dir;    // 实际落盘目录
  QString error;         // 空 = 成功
  bool ok() const { return error.isEmpty(); }
};

// 导出全部待处理报告：每份一个 <uuid>.dmp + 一份合并的 summary.txt，
// 成功后把该报告转入 completed（不删除，见决策 D5）
ExportResult ExportPendingReports(const QString& db_dir,
                                  const QString& target_dir,
                                  const AppInfo& info);

}  // namespace crash
```

实现放在 `crash_bootstrap.cpp`（两套模式都编译，内部 `#ifdef APP_ENABLE_CRASHPAD`
切换；自研模式下 `CountPendingReports` 恒返回 0、`ExportPendingReports` 直接
返回"无报告"）。同时把该文件里的 `init` / `resolveDumpDir` 一并改名 `Init` /
`ResolveDumpDir`（`crash::init` 只有 `main.cpp:319` 一处调用）。

**为什么用 UUID 而不是下标**：`GetPendingReports()` 每次返回的是新快照，库内唯一
稳定标识是 `Report::uuid`（`client/crash_report_database.h:69`），删除/转移接口也
都收 UUID（`:375` `SkipReportUpload`、`:384` `DeleteReport`）。按"导出第 i 个"的
下标式 API 实现，第一份导出并被转移后，快照里原本的第 i+1 项会顶到 i 位而被跳过。

**导出流程（逐份）**

1. `CrashReportDatabase::Initialize(db_dir)`；失败 → 视为 0 份（不打错误）。
2. `GetPendingReports(&reports)`；返回 `kBusyError` 等非 0 → 该轮跳过、不报错
   （Linux 实现对该情况直接跳过单份报告，Windows 侧会短暂独占锁，见 §6 风险）。
3. 逐份：`QFile::copy(report.file_path → <target>/<uuid>.dmp)`，比对目标大小与
   `Report::total_size` / 源文件大小；成功则 `SkipReportUpload(uuid,
   Metrics::CrashSkippedReason::kUploadsDisabled)`。
   **拷贝失败或大小不符 → 该份计入失败、不转移，报告留在 pending 下次再提示。**
4. `summary.txt`（人可读，开发者在打开 dump 之前先看它）：

```
应用:      demo_app
版本:      V0.1.0.123
git 提交:  a1b2c3d(-dirty)
构建配置:  RelWithDebInfo
平台:      Windows / x86_64        （或 Linux / x86_64）
崩溃时间:  2026-09-28 14:03:11     （Report::creation_time）
报告文件:  3f2a...c1.dmp (412 KB)  （Report::total_size）
导出时间:  2026-09-28 15:20:02
```

**不去解析 dump**：crashpad 没有 stackwalker，解析也拿不到调用栈；`Report` 结构体
里也没有 annotations 字段（注解只在 dump 内部）。

### 3.2 启动时检测 + 对话框（`src/app/`）

新增 `src/app/dialogs/crash_report_dialog.{h,cpp}`（沿用本仓对话框约定：
`initUi()` / `initSignals()` 分离、`QStringLiteral` 写中文、样式走 QSS 不写
`setStyleSheet`）：

- 文案："上次运行发生崩溃，已生成崩溃报告。请导出后发送给开发者。"
- 显示：待处理报告数、最近一次的崩溃时间。
- 按钮：[导出报告]（主按钮，用底座层的 `role="primary"` 动态属性，不用
  objectName 做样式角色）、[稍后]。
- 导出成功后弹 `QMessageBox`：显示导出的完整路径 + 提示"请把该文件夹发送给
  开发者"，并提供 [打开文件夹]（`QDesktopServices::openUrl`）。

导出位置：`QStandardPaths::DesktopLocation` → 取不到退 `DocumentsLocation` →
再退 `HomeLocation`，其下新建 `CrashReport-<yyyyMMdd-HHmmss>/`。**不压缩**：Qt5
没有公开的 zip 写入口，为压缩引入依赖不值当；两个文件客户右键压缩即可，提示
文案里写明。

挂载点（`main.cpp`）：基础设施块（Logger / GEH / `crash::Init`）之后、功能引导与
登录之前，用匿名命名空间的 `MaybePromptCrashReport()` 包起来：

- `opts.ui_test_script` 非空（回放模式）→ 跳过：模态框会打断回放。
- `opts.export_report_dir` 非空 → 走命令行导出（§3.3），不弹窗。
- **无桌面环境**（`QGuiApplication::platformName() == "offscreen"`）→ 跳过弹窗，
  只写日志，避免无人值守环境挂死在模态框上。

放登录之前而不是主窗口之后：崩溃可能发生在登录前（`crash::Init` 早于登录），
且这样对话框在没有主窗口时也能正常显示。

### 3.3 无 UI 的导出入口（演练与售后都靠它）

新增命令行选项 `--export-report [--export-dir <目录>]`：不弹窗，导出全部待处理
报告后退出。**两个选项而不是一个"取值可选"的 `--export-report [目录]`**：实测
Qt 只要给了 valueName，即便默认值传空串，`parser.process()` 仍会报
`Missing value after '--export-report'.` 并结束进程——"取值可选"在 Qt 里做不到，
拆成开关 + 目录既保留了"不写目录就用桌面"，又不必让人写假值
（退出码 0/1）。两个用途：

1. **演练可脚本化**：无桌面时也能把整条链路跑完（不需要点按钮）。
2. **售后兜底**：对话框因任何原因不可用时，让客户在命令行跑一次。

三个必须处理的细节：

- **不能被单实例逻辑吞掉**。现有 `HandleAlreadyRunning`（`main.cpp:261-266`）只对
  `--play` 特判，其余一律"转发给首实例后 `return 0`"——而转发对端只做窗口激活，
  不落地任何动作，脚本会看到**假成功**。故 `--export-report` 与 `--play` 同等对待：
  不转发、不因已有实例而退出，独立跑完导出再退出；数据库的并发访问由 crashpad
  自己的锁保护（最坏情况某份返回 busy 被跳过，下次再导）。
- **无桌面要显式关掉 GUI**：`QApplication` 在解析参数之前构造（`main.cpp:256`），
  没有 `DISPLAY` 时进程在构造阶段就死了。headless 机器上用
  `QT_QPA_PLATFORM=offscreen ./demo_app --export-report --export-dir <目录>`，
  写进指南。
- **Windows 是 WIN32 子系统程序**（`src/app/CMakeLists.txt:56`），没有控制台，
  交互式 cmd 也不会等它结束——退出码读不到。故由
  `cmake/template/export_crash_report.bat.in` 生成
  `export_crash_report.bat`，**放在可执行文件旁**（`bin/`，随安装包发到
  客户机上，规则 10：脚本用 Command Prompt、注释不用中文），内部
  `start /wait` 等应用退出并回显结果与退出码。客户双击即完成导出。

### 3.4 annotations 补充

`crash::Init()` 的入参从 `(handler_path, appName, appVersion)` 改为
`(handler_path, const AppInfo&)`，写进 CRASHPAD 的 handler annotations：
`git`（短 hash）、`build`（构建配置）、`os` / `arch`（编译期宏），保留现有的
`format` / `product` / `version`。

另有 `--crash` 选项：初始化完成之后主动触发一次空指针解引用，用于演练。
由 CMake 选项 `APP_ENABLE_CRASH_TEST`（默认 **ON**）控制是否编译进去，并只在该
开关打开时出现在 `--help` 里；发布包想摘掉就把它关掉（决策 D3）。

### 3.5 测试

`tests/core/crash_report_test.cpp`（仅 `APP_ENABLE_CRASHPAD=ON` 时注册）：

- **不依赖真崩溃，也不碰本机真实崩溃库**：用临时目录 + `QDir::tempPath()`，
  用 `PrepareNewCrashReport()` 写入若干字节 + `FinishedWritingCrashReport()`
  制造一份 pending 报告（该路径已核实可用：`crash_report_database_generic.cc:407`、
  `crash_report_database_win.cc:767`，随后由 `FinishedWritingCrashReport` 搬进
  `pending/`），全程走 §3.1 的**纯函数**（显式传 db_dir / target_dir / AppInfo），
  不调用 `crash::Init()`（测试二进制旁边没有 crashpad_handler）。
- 断言：`CountPendingReports(tmp_db)` 为 1；`ExportPendingReports(...)` 后目标目录
  出现 `.dmp` 且字节数一致、`summary.txt` 含版本与 git 提交、`error` 为空；数据库
  里该报告**不再出现在 pending**（转入 completed），文件仍在本地。

这让"导出"这一环在 CI / WSL 里无需 GUI、无需真崩溃即可验证。

## 四、演练（验收）

两平台各跑一遍：

1. 构建 `relwithdebinfo`（要 PDB / DWARF）。
2. `demo_app --crash` → 崩溃。
3. 重新启动：有桌面时走对话框点"导出"（Windows 用截图确认界面）；无桌面时
   `--export-report`（WSL 有 WSLg，两者都验）。
4. 开发者侧恢复堆栈，**这是唯一的硬验收**：
   - Windows：`cdb -z <dmp> -y <归档符号目录> -c "!analyze -v; kn; q"`，要求出现
     `demo_app!...` 的函数名与**行号**。
   - Linux：`lldb --core <dmp> <未 strip 的 ELF>` 取 `bt`，要求出现函数名与源码行。
5. 注解的验收口径：`summary.txt` 里有版本/git/构建配置（人可读），dump 内含
   （留档即可）——**不要求 cdb/WinDbg 里能看见注解**。

## 六、风险

| 风险 | 应对 |
|------|------|
| Windows 上取库会**短暂独占锁**（`crash_report_database_win.cc:329-337`） | 只在启动早期调用一次，不进循环/定时器；失败即视为 0 份继续启动。真出问题可让客户走 `--export-report` |
| 导出后报告转入 `completed/`，客户磁盘不再清理 | 本期不管；将来接 crashpad 的 prune 机制 |
| Linux 上无 lldb 时无法证明符号化 | 已确认本机 lldb 10 可用；CI 场景退化为"校验 dump 内模块 build id 与 ELF 一致" |
| `--crash` 被误用 | 由 `APP_ENABLE_CRASH_TEST` 控制，发布可关；`--help` 文案标注"仅用于验证" |
| 客户机器上数据库目录不可写 → 没有 dump | `crash::Init` 失败已打 WARN；导出时报错并给出路径 |

## 七、决策记录

- **D1 导出物形态**：目录（不是 zip）。Qt5 无公开 zip 写入口，为压缩引依赖不划算。
- **D2 对话框时机**：登录前；回放模式与无桌面环境跳过。
- **D3 `--crash`**：由 `APP_ENABLE_CRASH_TEST` 控制，模板默认 ON，发布可关。
- **D4 自研模式**：本期不导出，仅保证调用不崩；将来可把 `crash_*.log` 纳入同一个对话框。
- **D5 导出后不删除报告**：用 `SkipReportUpload(uuid, kUploadsDisabled)` 转入
  `completed/`——既不再提示，又不会因为客户把导出文件弄丢而永久失去唯一副本。
- **D6 报告标识用 UUID 不用下标**：见 §3.1。
