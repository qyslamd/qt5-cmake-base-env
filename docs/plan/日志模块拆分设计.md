# 日志模块拆分设计（Qt-free 静态库）

状态：已实施（2026-09-30）。审查记录见文末附录。

## 一、问题与目标

日志核心原来躺在 `src/core/logger/`，与 Qt 焊在一起：

| 类别 | 具体依赖 | 处数 |
|---|---|---|
| 线程 | `QMutex` / `QMutexLocker` | 12 |
| 路径与文件 | `QStandardPaths` / `QDir` / `QFile` / `QDateTime` / `QCoreApplication` | 16 |
| 配置 | `ConfigManager`（QObject 单例）→ `QVariant` → `QSettings` | 全部取配置处 |
| 信号 | `QObject::connect(&ConfigManager::…, configChanged, …)` | 1 |
| 界面 | `QObject` + `Q_OBJECT` + signals（`QtConsoleSink`、`LogHistoryBuffer`） | 2 个类 |
| 视图 | `QRegularExpression`（`log_filter`，只被日志面板用） | 9 |

（处数按出现次数计，含 `#include` 行；其中线程与视图两类各有几处在
`log_history_buffer.*` / `log_filter.*`，那两个文件本次不动。）

**为什么拆**：

1. `src/hal` 与 `src/measure` 是 Qt-free 的（2026-09-30 定），而设计里错误串要"同时进 `LOG_*`"。
   它们现在链不到日志：一链就把 Qt 拉回来。
2. 依赖方向反了：日志核心主动 `connect` 到上层的 `ConfigManager`。
3. 每次日志调用两次字符串分配：`LOG_INFO("MAIN", …)` 先隐式构造 `QString`，
   再在 `Logger::getLogger` 里 `module.toStdString()`，最后查 `unordered_map<std::string, …>`。

**目标**：把日志核心拆成不依赖 Qt 的静态库，Qt 侧只留薄桥；**调用点零改动**。

**非目标**：

- **不做动态库**。spdlog 在本仓是静态库（`3rdparty/spdlog-1.17.0/CMakeLists.txt:184,194`），
  而除日志外还有别处在直接用 spdlog（`core/crashhandler/global_exception_handler.cpp:148`
  的 `spdlog::default_logger()->flush()`）。日志一旦做成 DLL 链静态 spdlog，进程里就有两份
  spdlog 注册表，崩溃路径上 flush 到的是另一个空 logger。要做得把 spdlog 也变成 DLL。
- **不动 `main.cpp`**。它在 `eph-ad-auto-test` 与 `master` 上差 116 行（QtTesting 相关删改），
  碰它就会让 cherry-pick 到 master 起冲突。同理不动 `log_output_panel.cpp`、
  `global_exception_handler.cpp` 与 66 个 `LOG_*` 调用点。

## 二、拆分后的模块边界

```text
src/logging/             ← 新增，Qt-free，只链 spdlog::spdlog
  log_types.h                    LogLevel、LogPatternOptions、LogInitOptions（纯 POD）
  log_core.h / log_core.cpp      日志核心：初始化、模块 logger 注册表、级别、sink 组装、
                                 启动期缓冲、关闭；LOG_* 宏也在这里
  log_pattern.h / log_pattern.cpp 按开关拼 pattern 字符串（std::string 版）
  CMakeLists.txt                  ephad_log（STATIC）

src/core/logger/             ← Qt 侧，只剩桥
  logger.h / logger.cpp          Logger 门面：算路径、读配置、建 Qt sink、
                                 订阅 configChanged、调 LogCore::Init / ApplyOptions
  qt_console_sink.*              QtConsoleSink（原样）
  log_history_buffer.*           LogHistoryBuffer（原样）
  log_filter.*                   log_filter（原样：它是日志视图的过滤器，只有面板在用）
```

依赖方向：

```text
hal ─┐
     ├─→ logging ─→ spdlog        （无 Qt）
measure ─┘   ↑
             └── core/logger（Qt 桥）─→ core/config ─→ QSettings
app ─→ core/logger（门面）与 logging（宏）
```

`hal` / `measure` 本次**只链不调用**（它们现在一行 `LOG_*` 都没有）；这一层是为 P2 的真机
实现铺路——那时错误串要落日志。

## 三、接口

```cpp
// src/logging/log_types.h
enum class LogLevel { kDebug = 0, kInfo, kWarn, kError, kFatal };

struct LogPatternOptions {
  bool time = true; bool level = true; bool thread = false; bool module = true;
  bool source = false; bool func = false; bool message = true;
  bool colored_level = false;      // 控制台与界面 sink 为 true，文件 sink 为 false
};

struct LogInitOptions {
  std::string log_dir;             // 由调用方算好（Qt 侧用 QStandardPaths）
  std::string file_name;           // 不含扩展名，一般是 applicationName
  int pid = 0;                     // 主文件被占用时退到 <file_name>-<pid>.log
  std::size_t max_file_size = 10 * 1024 * 1024;
  std::size_t max_file_count = 20;
  int keep_days = 7;
  LogLevel level = LogLevel::kInfo;
  LogPatternOptions console_pattern;   // 控制台与界面 sink 用这套
  LogPatternOptions file_pattern;      // 文件 sink 用这套（差别只在是否着色）
};

// src/logging/log_core.h
class LogCore {
 public:
  static void Init(const LogInitOptions& options,
                   const std::vector<spdlog::sink_ptr>& extra_sinks = {});
  static void Shutdown();
  static spdlog::logger* GetLogger(std::string_view module);
  static void SetLevel(std::string_view module, LogLevel level);
  static void SetAllLevel(LogLevel level);
  static void ApplyOptions(const LogInitOptions& options);
};
```

几条定死的约束（都由审查逼出来，写在这里免得实现时走样）：

1. `ApplyOptions` **必须经 `spdlog::set_level()`**——它遍历 registry，已存在的模块 logger
   才会跟着变；只改全局变量的话，设置页改级别不会生效。
2. `ApplyOptions` 是**全量重放**（级别 + 两套 pattern 都按传入值重设），免得"改一个格式
   开关却把级别按旧值重设回去"。
3. `extra_sinks` 一律用 `console_pattern`——核心无从判断哪个额外 sink 是"控制台"，约定如此。
4. 启动期回放必须发生在默认 logger 与全部 sink **挂载之后**（`ReplayBootstrapLogs` 在
   `Init` 尾部），否则回放的行会掉进空气里。
5. `Shutdown()` 里放掉本库持有的 sink 引用（`g_console_sink` / `g_file_sink` /
   `g_extra_sinks`），否则 sink 比 spdlog 注册表活得久；调用方回收自己的 history buffer 时，
   sink 里那个裸指针就悬垂了。
6. 日志目录**由核心创建**（`std::filesystem::create_directories`）：`rotating_file_sink`
   自己不建目录，目录不在会抛异常并被降级路径吞掉，表现为"没有日志文件"这种难查的失败。
7. 模块名是 `std::string_view`：C++17 的 `unordered_map` 没有异构查找，所以注册表用带
   `std::less<>` 的 `std::map`，查表不分配。

`LOG_*` 宏移到 `log_core.h`，宏体只把 `Logger::getLogger` 换成 `LogCore::GetLogger`：

```cpp
#define LOG_INFO(module, ...)                                        \
  do {                                                               \
    auto* _l = LogCore::GetLogger(module);                           \
    if (_l) {                                                        \
      _l->log(spdlog::source_loc{__FILE__, __LINE__, ""},            \
              spdlog::level::info, __VA_ARGS__);                     \
    }                                                                \
  } while (0)
```

**66 处调用点零改动**：61 处模块名是字符串字面量，5 处是 `const char*` 变量
（`global_exception_handler.cpp:161`），两种都能直接绑到 `std::string_view`。

## 四、Qt 桥（`src/core/logger/`）

门面保持**同名同签名**，因此调用点一处不改：

| 现有调用 | 拆分后 | 变化 |
|---|---|---|
| `Logger::init()`（`main.cpp:279`） | 算路径/读配置 → 建 history buffer + `QtConsoleSink` → `LogCore::Init(opts, {qt_sink})` → 订阅 `configChanged` | 无 |
| `Logger::shutdown()`（3 处） | 转发 `LogCore::Shutdown()` → **放掉桥的 sink 引用** → `delete` history buffer | 无 |
| `Logger::qtConsoleSink()` / `qtHistoryBuffer()` | 门面持有并返回 | 无 |
| 66 处 `LOG_*` | 宏改调 `LogCore::GetLogger` | 无 |
| 8 处 `#include "logger/logger.h"`（不含 `logger.cpp` 对自己的相对 include） | 门面头文件原位不动，内部改为 `#include "logging/log_core.h"` | 无 |
| `Logger::setLevel(QString, …)` / `setAllLevel` | **零调用方**，删除；核心提供 `SetLevel(string_view)` | 删死代码 |
| `enum LogLevel` / `LOG_LEVEL_*`（旧） | 删除；全仓改用 `LogLevel` | 删死代码（否则与 core 的同名枚举冲突） |
| `log_pattern_builder.*` | `BuildLogPattern` 进核心；`LoadLogPatternOptionsFromConfig` 并进门面 `logger.cpp`；**两个文件删除** | 半个文件的尴尬没了，也避免核心反向依赖 ConfigManager |
| `LogPatternOptions`（旧，Qt 侧同名结构） | 删除，桥直接填核心的结构 | 同上 |

**为什么路径必须在桥侧算**：`QStandardPaths::AppLocalDataLocation` 的语义（含
organizationName/applicationName 两层）不是 `std::filesystem` 能随手复刻的。核心自己推路径
一旦与 Qt 差一点，日志就会悄悄搬到别处；而"搬家"这种问题事后极难发现。核心只接收算好的字符串。

## 五、逐项 Qt 依赖的处置

| 现依赖 | 拆分后 | 理由 |
|---|---|---|
| `QMutex` / `QMutexLocker` | `std::mutex` / `std::lock_guard` | 等价替换 |
| `QStandardPaths` 等算路径 | 调用方算好传进来 | 见上 |
| `QCoreApplication::applicationName()` / `applicationPid()` | `LogInitOptions.file_name` / `pid` | 同上 |
| 清理 `keep_days` 天前的 `*.log` | `std::filesystem` 遍历（MSVC 2019 与 WSL g++ 9.4 均无需额外链接项） | 纯 C++17，无平台分支 |
| 目录创建 | 核心 `create_directories` | 见约束 6 |
| 文件 sink 候选名降级（`423e7de`） | 原样保留 | 与 Qt 无关 |
| `ConfigManager` 取配置 | `LogInitOptions` 由桥填入 | 依赖反转 |
| `configChanged` → 热更新 | 桥里 `connect`，回调调 `LogCore::ApplyOptions` | 依赖反转 |
| `QString` 模块名 | `std::string_view` | 每次调用省两次分配 |
| `QtConsoleSink` / `LogHistoryBuffer` / `log_filter` | 留在 Qt 侧 | 界面职责 |
| `log_filter` 的 `QRegularExpression` | 不动 | 它是日志**视图**的过滤器 |

## 六、启动期缓冲

`GetLogger` 在未初始化时不再返回 `nullptr`（那等于把日志扔掉），而是落进核心里的启动期
缓冲（同步 sink，因为 `init_thread_pool` 还没跑），`Init()` 结束前按原级别回放、加
`[启动期]` 前缀。背景：`SingleInstance` 的构造与"是否已有实例"的判定都在 `Logger::init()`
之前，而那段恰好是"程序为什么一闪就退"最需要的线索。

**已知缺口**：第二实例在 `main.cpp:253` 就 `return *exit_code`，走不到 `Init()`，所以它的
`检测到已有实例运行` 仍然不落盘。补它要动 `main.cpp`，与非目标冲突，本设计**不含**。
