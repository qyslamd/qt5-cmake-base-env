# 界面路线开关下沉到目标设计

状态：**一轮审查 10 条已处置**（2026-10-14），待二轮审查。

## 一、问题与目标

### 现状

`APP_UI_ROUTE` 是顶层 `CMakeLists.txt:84-88` 的缓存变量，路线因此成了**整个
构建目录**的属性。代价：

- fluent 要独立构建目录（`-DAPP_UI_ROUTE=fluent` + `-B build/...-fluent`），
  两份 700 MB 级目录、`temp/fluent_build.bat` 这类辅助脚本都因此而生
- 缓存覆盖只存在于 CMakeCache（删缓存即静默回默认），是规则 18/19 反复踩的坑
- 顶层长了一个不属于它的职责——顶层该做的只是组织第三方依赖

### 目标

1. 路线下沉为**目标/目录属性**：同一构建目录里 demo_app 可走 fluent、examples
   走 qss
2. 顶层收敛回组织依赖（QWindowKit/SARibbon/FluentUI3Style 的
   add_subdirectory 顺序与开关）
3. 源码零改动（宏判据归一除外，见 §三.6），运行期行为不变

### 非目标

不做运行期切换——窗口基类是编译期定的，另案讨论过、已否决。

文档），外加一处不挂这三个名字、但**以 `BUILD_RIBBON` 为判据的路由消费点**：

## 三、方案

1. **顶层删缓存、改普通变量默认值**：删 `:84-85`（缓存 set 与
   `set_property(CACHE ... STRINGS)` 两行一起，§二 已述后者会炸），`set(APP_UI_ROUTE "qss")`
   普通变量；`:86-89` 值域校验保留（校验的是默认值，恒合法；子目录覆盖值自己
   负责，非法值在 `STREQUAL "fluent"` 判断下自然走 qss 分支）
2. **不用 `option()`**：option 是缓存语义，缓存里已有同名条目时不覆盖——
   正好复活规则 19 的坑。普通变量不进 CMakeCache，改了下次 configure 就生效
3. **三层覆盖**：顶层默认（qss）→ `local.cmake` 覆盖（不入库的本地切换）→
   子目录 `set`（目标级固定，兄弟目录互不可见）。目录作用域普通变量在
   add_subdirectory 时拷贝给子目录，天然隔离
4. **src/app 的 if/else 形状保留**（含 `APP_UI_ROUTE=fluent 需要
   BUILD_FLUENT_UI=ON` 的 FATAL_ERROR 校验），只是判的对象从缓存变量换成
   继承/覆盖后的值
5. **`BUILD_RIBBON`/`BUILD_FLUENT_UI` 语义维持现状**（默认均 ON）：既管编不编
   那个库，也管 qss 路线下 demo_app 的主窗口形态（`APP_ENABLE_RIBBON`）。方案
   对这两个 option 零改动
6. **demo_app 实际路线发布为全局属性**（一轮审查 🔴 的修复）：src/app 的
   if/else 判定后 `set_property(GLOBAL PROPERTY APP_DEMO_UI_ROUTE ...)`。
   `tests/funq_app` 的 `FUNQ_RIBBON` 判据从 `if(BUILD_RIBBON)` 改为
   `BUILD_RIBBON AND NOT fluent`（读全局属性）。为什么用全局属性而不是
   PARENT_SCOPE：tests/ 与 src/app 是兄弟目录，PARENT_SCOPE 要 src/app → src →
   顶层逐层链才能到 tests，全局属性一步到位、跨目录可见。这样
   `test_app_shell.py` 的交叉断言（`FUNQ_RIBBON` 与实际界面形态一致，
   `:142-155`）在两条路线下都成立
7. **示例宏归一 + 宏库解耦**：只留 `APP_UI_FLUENT`，fluent 路线才定义；qss 是
   缺省形态、无宏。四个示例统一为：`if(fluent)` 注 `APP_UI_FLUENT`，`else()`
   链 `${APP_TARGET_PREFIX}_style`；main.cpp 的 `#ifdef APP_UI_QSS` 改
   `#ifndef APP_UI_FLUENT`。**链 FluentUI3Style 的只有 new_login_dialog**——
   它的 fluent 分支要 `new FluentUI3Style`；其余三个示例（fft_demo /
   funq_target / tour_demo）fluent 分支是空操作（维持系统默认样式的现状），
   **只注宏不链库**，避免链上不用的死依赖
8. **文档与配方**：README:82-87 的 `-D` 配方删除（普通变量会**静默遮蔽**
   `-DAPP_UI_ROUTE`，CMakeCache 里还留下一条无效缓存——不改就是下一个规则
   19 坑）；本机 `temp/fluent_build.bat` 用同一配方，单目录后已无用，删除；
   CLAUDE.md 双路线说明与规则 18 例子、plan总结「落地形态」段补决策记录；
   CHANGELOG 是历史，不动
9. **迁移期防静默回退**：顶层加一段 configure 期检查——
   `if(DEFINED CACHE{APP_UI_ROUTE})` 则 `message(WARNING ...)` 提示缓存残留
   已无效、用 `cmake -U APP_UI_ROUTE` 清掉。不然本机现存的 fluent 构建目录
   重新 configure 会静默变回 qss，§一 要消灭的坑由方案自身重演一遍

## 四、funq / 测试影响

- qss 路线（默认）：用例与判据全不动，ctest 数量不变
- fluent demo_app：一轮审查抓出 `FUNQ_RIBBON` 交叉断言必红——已由 §三.6 修复
  （期望值随 demo_app 实际路线走）；用例本身（alias 定位、
  `funq.action(...).trigger()`、`RIBBON_ENTRIES`/`MENU_ENTRIES` 两头解析）
  双形态兼容，不动
- `funq_target` 与示例不随 demo_app 的路线走

## 五、验收

1. **混编**（本方案的靶心）：`src/app/CMakeLists.txt` 里
   `set(APP_UI_ROUTE fluent)` + examples 默认 qss，单一构建目录 configure +
   `relwithdebinfo -a x86` 全量编过；demo_app 起 Fluent 壳（QMainWindow +
   Fluent 标题栏），任一示例起 qss 形态；**ctest 全绿**（含 FUNQ_RIBBON 交叉
   断言）。**验证完回退这一行**——它入库波及全仓；长期切 fluent 走
   `local.cmake`（只影响本机，不入库），两条路波及面不同
2. 默认形态（全 qss）：ctest 与改动前一致
3. `local.cmake` 写 `set(APP_UI_ROUTE fluent)` 覆盖生效，且不入库
4. `grep -rn APP_UI_QSS` 归零（除 CHANGELOG 与 docs/）；`APP_UI_ROUTE` 只剩
   CMake/文档消费点
5. 迁移 WARNING：拿存有 `APP_UI_ROUTE` 缓存的旧目录重新 configure，出提示
6. 打包冒烟（`-t relwithdebinfo -p`）：FluentUI3Style.dll 照常随包

## 六、决策记录（2026-10-14）

1. **默认 qss**：现状不破坏；切 fluent 走 `local.cmake`（本机、不入库）；
   `src/app` 里 set 属于入库的全仓固定，仅验收时临时用、验完回退
2. **普通变量，不用 option()**：缓存语义复活规则 19 的坑
3. **宏归一只留 `APP_UI_FLUENT`**：缺省形态无宏
4. **宏库解耦**：三个空操作示例只注宏不链 FluentUI3Style，避免死依赖；
   new_login_dialog 是唯一真用 Fluent 的示例
5. **FUNQ_RIBBON 随实际路线**（一轮审查 🔴）：判据从 `BUILD_RIBBON` 改为
   `BUILD_RIBBON AND NOT demo_app fluent`，经全局属性跨目录传值
6. **不做运行期切换**：另案否决（窗口基类编译期定）
