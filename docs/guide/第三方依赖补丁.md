# 第三方依赖补丁

本仓把第三方源码的压缩包放在 `3rdparty/`，首次 configure 时解压到同名目录
（`cmake/extract_dependencies.cmake`）。**解压产物不入 git**，所以对上游源码的
改动不能直接改在解压目录里——重解压就丢，也没法 review。留得住的改法只有两种：
上游有开关就用 option，没开关就打补丁。

## 目录与注册

```text
patches/
├── <库名>/NNNN-<描述>.patch      补丁本体，入 git，行尾钉死 LF
└── tools/*.py                    生成补丁的脚本（见「生成补丁」）
cmake/patch_dependencies.cmake    逐条注册 + 在 configure 阶段应用
```

新增一条补丁：

1. 补丁放进 `patches/<库名>/`，按 `NNNN-` 编号（只是本仓的应用顺序，与上游
   文件名无关），格式要是 `git apply` 默认 `-p1` 认的那种（`a/`、`b/` 前缀）
2. 在 `cmake/patch_dependencies.cmake` 末段加一句
   `apply_patch_to_dir("${3RDPARTY_DIR}/<解压目录名>" "${PATCHES_DIR}/<库名>/NNNN-xxx.patch")`，
   并在紧邻处写一句**为什么**——上游没有开关、还是上游自己写错了。下游看到
   这条补丁时，只能靠这行注释知道它为什么存在
3. 重跑 configure：补丁只在配置阶段打

configure 输出里的 `[OK]   <stem>` / `[SKIP] <stem>` 是判断补丁有没有生效的
唯一可靠信号。

## 打补丁还是用 option

判据：**上游的构建选项能表达的，绝不打补丁**。补丁只给"没有开关可关"和
"上游自己写错了"这两类情况兜底。

| 实际例子 | 走哪条 | 为什么 |
|---|---|---|
| spdlog 的示例与测试 | option | 上游有 `SPDLOG_BUILD_EXAMPLE` / `SPDLOG_BUILD_TESTS` |
| SARibbon / QWindowKit 的静态库与模块选择 | option | 上游有 `SARIBBON_BUILD_STATIC_LIBS`、`QWINDOWKIT_BUILD_WIDGETS` 等一整套 |
| kissfft 的测试与命令行工具 | option | 上游有 `KISSFFT_TEST` / `KISSFFT_TOOLS`（默认还是 ON，见下） |
| `cmake_minimum_required` 低于 3.5 | 补丁 `zlib/0001`、`SARibbon/0002` | 不是选项；CMake 4.0 起删掉了对 <3.5 的兼容，不改 configure 直接失败 |
| 做「版本无关查找」（`find_package(QT NAMES Qt6 Qt5)`）的库 | 补丁 `QXlsx/0001`、`SARibbon/0001`、`funq/0002`、`FluentUIStyle/0001` | 那种查找走包名 `QT`、认 `QT_DIR`，与本仓 `local.cmake` 只给 `Qt5_DIR` 的写法对不上 |
| zlib 给自己四个示例程序无条件 `add_test` | 补丁 `zlib/0002` | 没有开关可关，而那四个目标本仓从不编译，纯让 ctest 多出两条 `Not Run` |
| SARibbon 的 `install(TARGETS … EXPORT)` | 补丁 `SARibbon/0004` | 本仓是树内消费者，导出规则只会碍事（同 FluentUIStyle，见下） |

## 两个不能省的命令行开关

`cmake/patch_dependencies.cmake` 里已经钉死，手工调试时也别漏：

- **`GIT_CEILING_DIRECTORIES=<解压目录的父目录>`**：解压产物是被 `.gitignore`
  忽略的未跟踪文件，而 `git apply` 拒绝改动这类文件——它会**静默 skip 并返回
  0**。退出码骗人：不设这个变量时，"补丁打了"与"补丁被跳过"看起来一模一样。
  把父目录设为 ceiling，git 就认为它不在任何仓库里，这层保护随之失效。
- **`-c core.autocrlf=false --ignore-whitespace`**：补丁钉的是 LF，而个别上游
  源码是 CRLF（SARibbon 的 CMakeLists 就是）。不关 autocrlf，被补丁改过的
  整个文件会被写成 CRLF；不带 `--ignore-whitespace`，行尾不一致会让按行匹配
  直接报 `patch does not apply`。代价是补丁改过的那几行按 LF 落盘、目标文件
  成为混合行尾——CMake 两者都认，且该文件每次重解压重新生成，可接受。

## 幂等与失效

apply 成功后在同目录写 `.patch_applied_<补丁名>` 标记，下次 configure 见到就
跳过。三种情况标记与实际状态会对不上：

- **改了补丁内容、标记还在** → 不会重放。删掉那个标记文件再 configure
- **删了解压目录** → 标记随目录一起消失，下次 configure 重新解压并打全
- **解压目录残缺**（例如上次构建的残留进程占着 DLL，删不掉又"见目录存在"
  就跳过解压）→ 补丁会打在残缺的树上，报一堆 `No such file or directory`。
  处理见 [funq 注入式 UI 测试](funq注入式UI测试.md) 的「排错」

## 生成补丁

`patches/tools/` 里留下两个脚本（SARibbon / QWindowKit 的四条、funq 的
0008），脚本头的 docstring 写明 pristine 工作目录怎么重建。套路是：

1. 把依赖解压到一个**干净目录**（别放 `3rdparty/`，免得 configure 见目录存在
   就跳过解压）
2. 在它上面直接改到满意，用 `diff -ruN <pristine> <改后>`（或
   `git diff --no-index`）出差异
3. 整理成 `patches/<库名>/NNNN-xxx.patch`，路径前缀对齐 `3rdparty/<解压目录>`
   的相对位置
4. **先 `git apply --check` 验一遍再注册**——hunk 的行数写错报 `corrupt
   patch`、上下文差两行报 `does not apply`，都是手写补丁的常客
5. 删掉那个干净目录，它的使命就这一次

## 接一个新依赖的检查单

除了"压缩包放 `3rdparty/` + 登记进 `DEPENDENCY_ARCHIVES`"（清单同时驱动清理
脚本 `scripts/clean_deps.*`，不用手动同步），本仓踩过这几条：

**依赖的 `option()` 与本仓同名。** 这是踩过的坑（当时的当事库是 FFTW，它自己
也有 `BUILD_TESTS`，而本仓顶部也是 `option(BUILD_TESTS ...)`；FFTW 已随 kissfft
的接入下线，但这个坑对后续任何新依赖都成立）。这时**不能**写
`set(BUILD_TESTS OFF CACHE BOOL "..." FORCE)`——那会覆盖本仓选项的缓存值，把
整个仓库的单元测试一起关掉，而且后果是**静默的**：`CTestTestfile.cmake` 与
测试二进制都是上一轮留下的（CMake 的生成物只增不删），`ctest` 照样报通过。
正确写法是作用域内的普通变量：

```cmake
set(BUILD_TESTS OFF)            # 普通变量，不是 CACHE
set(BUILD_SHARED_LIBS OFF)
add_subdirectory(3rdparty/xxx)
unset(BUILD_SHARED_LIBS)
unset(BUILD_TESTS)
```

前提是**依赖的 `cmake_minimum_required` ≥ 3.13**：CMP0077 为 NEW 时，
`option()` 见到同名普通变量就不覆盖、也不建 cache 条目。低于 3.13 的依赖得
先补一条抬版本的补丁——`zlib/0001`、`SARibbon/0002` 正是这么来的。

**依赖的测试/工具默认 ON，且要 pkg-config。** kissfft 是最新的一例：
`KISSFFT_TEST` / `KISSFFT_TOOLS` 默认 ON，而它们的 CMakeLists 里直接
`pkg_check_modules(libpng/fftw3 REQUIRED ...)`——缺 pkg-config 时 configure
**直接 FATAL**（不是"多几个用例"那么轻）。接新依赖时先扫一眼默认 ON 的
`*_TEST` / `*_TOOLS` / `*_EXAMPLES`。

**不要给带 `install(TARGETS … EXPORT)` 的依赖补 `INTERFACE_INCLUDE_DIRECTORIES`。**
导出目标的接口里不允许出现源码树 / 构建树路径，CMake 在 generate 阶段直接报
`INTERFACE_INCLUDE_DIRECTORIES property contains path ... which is prefixed in
the source directory`。要包含目录就由消费者自己加——本仓对 crashpad 就是这么
做的。（正面对照：kissfft 的 target 自带 `PUBLIC` 的 `BUILD_INTERFACE` 头路径，
`fft_demo` 因此一行 include 都不用写。）

**依赖自带的 `install()` 规则会外溢，必要时关掉它。** FluentUIStyle 是最新
的一例：它有一套完整的 `install(TARGETS …)` + 头文件目录 + `install(EXPORT …)`，
带来两个后果——① 它 `install(EXPORT FramelessTargets)` 而 Frameless 链的
`QWKWidgets` 没进任何导出集（本仓 `QWINDOWKIT_INSTALL=OFF`），**generate 阶段
直接报错**；② Linux 的 AppImage 走 `cmake --install`，规则留着会把它的头文件
与 cmake 包配置装进 AppDir。本仓的解法不是打补丁，而是**作用域内的
`CMAKE_SKIP_INSTALL_RULES`**：

```cmake
set(CMAKE_SKIP_INSTALL_RULES TRUE)      # 只影响这一支
add_subdirectory(3rdparty/xxx)
unset(CMAKE_SKIP_INSTALL_RULES)
```

变量在 `add_subdirectory` 调用时被继承，撤掉之后本仓自己的安装规则（AppImage
要用）不受影响——实测有效。

**依赖自带的 `add_test` 会污染本仓的 ctest。** zlib 最典型：它给四个示例程序
无条件注册测试，而那些目标本仓根本不编，于是 ctest 里多出两条 `Not Run`。
能关就关，不能关就补丁删掉整段。

**依赖用 `find_package(QT NAMES Qt6 Qt5)` 找 Qt 时，宿主得先把
`QT_VERSION_MAJOR` 钉死。** qmsetup（QWindowKit / FluentUIStyle 都带它）的
`qm_find_qt` 只在 `QT_VERSION_MAJOR` 未定义时才做"版本无关查找"——那个查找走
包名 `QT`、认 `QT_DIR`，与本仓 local.cmake 只提供 `Qt5_DIR` 的写法对不上，**直接
配置失败**。顶层 `CMakeLists.txt` 因此显式 `set(QT_VERSION_MAJOR 5)`，让它转回
`find_package(Qt5 ...)`、复用已解析的 `Qt5_DIR`。

**只给 `Qt5_DIR` 时，别的 Qt 包要经 `find_package(Qt5 COMPONENTS ...)` 找。**
CMake 不会因为 `Qt5_DIR` 指向 Qt 的 `lib/cmake` 就去那里找 `Qt5LinguistTools`：
直接 `find_package(Qt5LinguistTools)` 实测 NOTFOUND，而走 Qt5 的 components
机制时 `Qt5Config` 会自己按 `Qt5_DIR` 推出 `Qt5LinguistTools_DIR`。本仓的
lrelease 是这么找到的，且刻意不带 `REQUIRED`——它来自 qttools，装机可能没有，
缺了只该失去翻译。

**只摘依赖的一部分子目录时，上游顶层 CMakeLists 里设的全局开关会丢。**
qlitehtml 是最新的一例：本仓只 `add_subdirectory` 它的 `src/`（它的顶层会
`include(local.cmake)`、还会建 `tests/manual/browser`），而 `CMAKE_AUTOMOC ON`
恰恰写在顶层那份里——漏了它 `QLiteHtmlWidget` 就没有 moc，链接期报一屏
`staticMetaObject` / `qt_metacall` 找不到，编译期却一声不吭（本仓在
`add_subdirectory` 之后补了 `set_target_properties(qlitehtml PROPERTIES
AUTOMOC ON)`）。摘子目录前先把顶层扫一遍：`AUTOMOC` / `AUTOUIC` / `AUTORCC`、
`CMAKE_*_OUTPUT_DIRECTORY`、版本变量（上游 `QLITEHTML_VERSION` 取的是
`${PROJECT_VERSION}`，只加 `src/` 时会取到**本仓**的版本号），都可能在那一层。

**上游自带 git 子模块时，克隆/branch 归档都不含子模块内容。** qlitehtml 的
`src/3rdparty/litehtml` 是 submodule（指向 Qt 自己的 fork），空的；本仓单独供
上游 litehtml 0.10——已逐文件 md5 比对，两者逐字节相同。做法是**先建出同名
target**（`add_subdirectory(3rdparty/litehtml-0.10)`），qlitehtml 的
`if(NOT TARGET litehtml AND EXISTS ...)` 分支自然跳过，不必打补丁。

**上游源码是「解压即弃」还是「入库」决定了补丁往哪放。** 本仓两种都有：qlitehtml
是**源码入库**（`3rdparty/qlitehtml` 的 256 个文件都在 git 里，当年给 Qt 5.12 打的
`QT_VERSION_CHECK` 守卫直接提交在源码上）；quickjs-ng 是**解压即弃 + 补丁脚本**
（两处 MSVC 编不过的改动在 `patches/quickjs/` 里，由 `patch_dependencies.cmake`
在 configure 阶段应用）。选哪种看包的大小与要不要跟上游对齐，但**别把补丁写在
解压目录里**——重解压就丢。

**提交生成物时，配方要一起入库。** `src/markdown/resources/mathjax-svg.min.js`
是 esbuild 打出来的 1.5MB JS，入库的理由是它与平台无关（纯 JS，实测 Windows 与
Linux 产物等价），省掉两个平台各装一套 node 工具链。代价是它**不可读、不可
review**，所以生成入口（`mathjax_svg_entry.mjs`，头注释里写明 node/esbuild 版本
与两个 `--define` 参数）必须一起提交，否则没人能重建它。

Mermaid 那三份（`resources/mermaid.js`、`dom_shim.js`、`path_bbox.js`）是同一
个道理：从 `mermaidx-0.9.5` 逐字节取来的纯 JS（官方 bundle 内含 mermaid
11.16.0），入库入 qrc。配方与三份的 md5 写在
`src/markdown/resources/extract_mermaid_payload.py` 里，升级时跑 `--check` 对
哈希。注意 **mermaid 的版本看 bundle 里的 `version:"11.x.y"`，与 mermaidx 的
版本号互相独立**。

## 许可

选型先看这一节。本仓的依赖里有**两个 GPL 类**，其余是宽松许可：

| 依赖 | 许可 | 用在哪 |
|---|---|---|
| QCustomPlot | GPL-3.0-or-later | `demo_app` 与 `examples/fft_demo` 的绘图（早于本文档就在仓库里） |
| qlitehtml | GPL-3.0-only WITH Qt-GPL-exception-1.0，或 `LicenseRef-Qt-Commercial` | `src/markdown` 的渲染控件（官方仓库 `code.qt.io/playground/qlitehtml`） |
| litehtml / gumbo / md4c | BSD-3-Clause / Apache-2.0 / MIT | 随 qlitehtml 与 `src/markdown` 进来 |
| mermaid（官方 bundle） | MIT | `src/markdown/resources/mermaid.js`（内含 mermaid 11.16.0） |
| mermaidx 的 `dom_shim.js` / `path_bbox.js` | MIT | 同上目录，取自 mermaidx-0.9.5 |
| QtTesting | BSD-3-Clause（Kitware，与 Qt 公司无关） | UI 录制回放 |
| spdlog / googletest / SARibbon / QXlsx / qwindowkit / FluentUIStyle / kissfft / crashpad 系 | MIT 或 BSD 系 | — |

关于 qlitehtml 的例外条款：`Qt-GPL-exception-1.0` 的 Exception 2 允许"把本程序
与按你自选许可的插件结合成可执行文件并按你的条款分发"，**条件是**可执行文件
必须附带显著声明、向所有用户提供本程序（即 qlitehtml，含你的改动）的完整源码；
独立模块（业务代码）不在其列。闭源静态链接是否恰好落进这个例外属于法务判断，
本仓不做结论——要对外分发闭源产品，先与法务确认或走 Qt 商业授权。

**曾经写在 kissfft 段里的"不选 FFTW 是因为 GPL 会把业务代码一起拽进去"，只针对
FFT 那一个位置**；说"本仓没有 GPL 类依赖"是不成立的（QCustomPlot 就是）。
新接 GPL 类依赖时按 QCustomPlot / qlitehtml 的先例办：许可在这里登记，
用途在 `模板使用指南.md` 的「可保留的示例」里点明。
