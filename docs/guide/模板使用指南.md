# 模板使用指南

本仓库即"Qt5 + CMake + Ninja"项目基础模板。Windows 主线为 MSVC，同时
支持 Linux/GCC 构建（见下文"Linux 构建"）。

基于它新建项目时，按下面的必改项清单修改即可，其余构建设施（版本管理、
部署、打包、符号归档、代码统计、单元测试）无需改动。

## 必改项

| # | 位置 | 改成什么 |
|---|------|----------|
| 1 | `CMakeLists.txt` 顶部 `PROJECT_NAME_STR` | 项目名。未改时 configure 会输出 WARNING |
| 2 | `CMakeLists.txt` 顶部 `APP_ORG_NAME` / `APP_APP_NAME` / `APP_URL` | 组织名、应用名与项目主页。前两者决定 `%LOCALAPPDATA%` 数据目录（配置/日志/崩溃）、单实例键、窗口标题，以及安装包的发行者与安装目录层级；改名后旧数据目录不会自动迁移。`APP_URL` 留空则安装包不显示链接 |
| 3 | `CMakeLists.txt` 顶部 `APP_TARGET_PREFIX` | 目标名前缀，预设为 `demo`，拼出 `demo_core` / `demo_app`。它决定 exe 文件名、运行脚本名与打包脚本中的目标名，改这一处即可，无需逐个模块改 `TARGET_NAME` |
| 4 | `local.cmake`（仅 Windows）与 `.vscode/settings.json` 的 `qtcmake.qtDir` | 本机路径，两处需一致：前者供构建（含 Qt 安装路径 x64/x86 两条；该文件不入库，首次 configure 时若不存在会自动生成并报错提示），后者供 VS Code 调试时定位 Qt 的 DLL 与插件。Linux 不读取 `local.cmake` |
| 5 | `CMakeLists.txt` 顶部 `APP_INSTALLER_ID_X64` / `APP_INSTALLER_ID_X86` | 安装包产品标识（Inno Setup 的 AppId），每个项目必须换新 GUID，否则安装包互相覆盖。配置阶段检测到模板默认值会输出 WARNING；可用 pwsh 执行 `[guid]::NewGuid()` 生成 |
| 6 | `src/app/resources/icons/icon.ico`（Windows）与 `icon.png`（Linux） | 程序图标：前者嵌入 exe 版本资源并用于安装包，后者供 AppImage 使用（256×256 PNG）。两平台图标各自独立，换 logo 时两个都要换 |

以下项已有合理默认，无需修改，需要时再调整：

- 安装包的显示名、发行者、安装目录层级与链接：全部由 `APP_APP_NAME` /
  `APP_ORG_NAME` / `APP_URL` 派生，`cmake/make_install_package.iss.in`
  中不含任何需要手改的字面量。安装目录为 `{autopf}\<组织名>\<应用名>`，
  与 `%LOCALAPPDATA%` 下的数据目录同构
- 安装包图标：`cmake/make_install_package.iss.in` 的 `MyInstallerIcon`
  （默认取程序图标）
- 版本号：由 git 派生 —— 最近的 `v1.2.3` 形式 tag 提供前三段，提交总数提供
  build 号，exe 版本资源中还记录 git 短 hash（工作区有改动时带 `-dirty`）。
  同一提交在任何机器上构建得到同样的版本号。无 git 环境时回落 `0.0.0.0`，
  需要固定版本号时用 `-DAPP_VERSION_OVERRIDE=major.minor.patch.tweak` 指定
- `APP_ARCH_SUFFIX`（x64/x86）与 `APP_MUTEX_NAME`：
  由 `CMAKE_SIZEOF_VOID_P` 与 `APP_APP_NAME` 自动派生

## 目录结构

```text
src/
├── core/    demo_core    无 UI 依赖：配置 / 日志 / 崩溃 / 认证 / 单实例
└── app/     demo_app     界面骨架、资源与样式
    └── qttesting/        UI 录制/回放接线（仅在 BUILD_QT_TESTING 打开的构建里编译）
external/
└── qt-libui              通用 UI 部件（git submodule，随本仓一起编译）
tests/
├── core/    单元测试与子进程崩溃用例
└── app/     demo_app 的 UI 回放测试
```

依赖方向为 `app → core`，以及 `app → qt-libui → Qt`。通用 UI 部件（启动
画面、滑块开关、环形/扇区菜单、进度条族、标签栏外观）位于独立仓库
**qt-libui**，以 git submodule 引入到 `external/` 下并源码内嵌构建：

- 克隆本仓时需一并拉取：`git clone --recursive`，或事后
  `git submodule update --init --recursive`
- 顶层 `CMakeLists.txt` 中 `add_subdirectory(external/qt-libui)` 引入，链接
  `qt-libui::libui`；头文件仍写 `#include <qt-libui/...>`
- 该库按「非顶层构建」处理自己：不读自己的 `local.cmake`、不编 gallery
  示例、不登记 install 规则，因此不会往本仓安装目录里塞东西
- 改库代码：在 `external/qt-libui` 内切到分支开发（submodule 默认处于
  detached HEAD），提交并推送后，回本仓提交一次 submodule 指针更新

## 可保留的示例

以下内容作为用法示例保留，新项目可在此基础上替换成自己的业务代码：

- `src/app` — 主窗口（功能区/菜单栏 + 占位中央控件）、登录、设置、关于、日志窗口
- `src/core/logger` — spdlog 封装（`LOG_INFO` 等宏），建议保留
- `src/core/auth`、`config`、`crashhandler` — 按需保留
- `config/calibration/calibration_sample.ini` — 构建后自动拷贝为
  `bin/calibration/calibration.ini`，是"配置文件随构建输出"的示例
- `tests/core/crashhandler_test.cpp` — 单元测试与子进程崩溃测试的样例

## 按需裁剪

- 顶层 `CMakeLists.txt` 中 3rdparty 的 `add_subdirectory`
  （spdlog、googletest、QCustomPlot、QXlsx）及对应 `target_link_libraries`

- `src/app/CMakeLists.txt` 中 calibration 拷贝的 POST_BUILD 示例

## 单元测试

测试放在 `tests/<模块>/`，用 `add_unit_test` 宏注册（宏定义在
`cmake/test_helpers.cmake`，由 `tests/CMakeLists.txt` 引入）：

```cmake
add_unit_test(
    NAME test_core_crashhandler
    SOURCES crashhandler_test.cpp
    LIBS ${APP_TARGET_PREFIX}_core
    QT_MODULES Core Test
    LABELS CORE
    NO_GTEST_MAIN
)
```

| 参数 | 说明 |
|------|------|
| `NAME` | 测试目标名，约定 `test_<模块>_<被测对象>` |
| `SOURCES` | 源文件列表 |
| `LIBS` | 额外链接的库 |
| `INCLUDES` | 额外头文件路径 |
| `QT_MODULES` | 依赖的 Qt 模块，自动加 `Qt5::` 前缀并开启 AUTOMOC |
| `LABELS` | CTest 分组标签，便于 `ctest -L` 过滤 |
| `NO_RUN_SCRIPT` | 不生成运行脚本 |
| `NO_GTEST_MAIN` | 不链接 `gtest_main`（测试自提供 `main`） |

构建后：

```bash
ctest --test-dir build/ninja-debug-x64 --output-on-failure
```

测试可执行文件位于 `<构建目录>/bin/tests/`，与生产产物隔离。

## UI 测试（录制 / 回放）

界面回归用 QtTesting 驱动：录一遍操作存成 XML 脚本，之后改完代码回放一遍，
就能发现界面有没有被踩坏。接线代码在 `src/app/qttesting/`。

> 另一条思路是**注入式**：不改被测程序，测试时把库注入运行中的进程，用 Python
> 写用例按控件操作并断言属性。仓里另有一套基于 funq 的实现（被测程序是
> qt-libui 的 gallery 示例），见 [funq 注入式 UI 测试](funq注入式UI测试.md)。

**开关**：`BUILD_QT_TESTING`，默认 ON，各构建类型都能用。QtTesting 是静态库，
开着会整套链进 exe，并在主窗口挂出「测试」菜单；准备发布包时用
`-DBUILD_QT_TESTING=OFF` 关掉，省一份编译与体积。

**录制**：Debug 构建启动程序，菜单「测试 → 录制事件…」选一个 XML 文件，之后
在主窗口上的操作会被记录；再次点开该菜单即可停止。

**回放**：

```bat
build\ninja-debug-x64\bin\demo_app.exe --play <脚本.xml>
```

播完即退出，退出码就是结果（0 成功、1 失败），可直接接进 ctest：

```cmake
add_test(NAME my_uitest
    COMMAND $<TARGET_FILE:${APP_TARGET_PREFIX}_app> --play <脚本.xml>)
```

`tests/app/` 下已有一条这样的接线（`test_app_uitest_playback`），跑的是空事件
脚本，验证「能启动、能装载脚本、能按结果退出」这条链路本身。

**回放会跳过登录**：录制入口在主窗口菜单里，也就是录制总是从「已登录」状态
开始；回放只有从同一状态起步，脚本里记录的控件才存在。所以登录对话框本身不
在这条链路的覆盖范围内——要测它得另想办法（例如把录制起点挪到登录前）。

**两条注意**：回放依赖真实的窗口与事件循环，无桌面环境（纯 CI 容器）里跑不了；
脚本里的控件路径是**「序号 + 类名」**（形如 `1MainWindow0/1QMenuBar0/menuTool`，
功能区形态下这一段则是 `1MainWindow0/1SARibbonBar0/...`），不是 `objectName`
——所以控件改名固然会失效，**增删同层控件、调整布局顺序同样会失效**，而且不报错，
只表现为回放失败或点到别处。这是它和 funq 那套（按 `objectName` 走 `::` 路径）
最实际的区别。

**窗口都得有应用内关闭按钮。** 回放**录不到标题栏的 X**：标题栏属非客户区，关闭
由系统处理、直接发 `QCloseEvent`，**没有鼠标事件经过录制器的过滤器**；而库里也没有
任何 player 支持 `close` 命令——想在 XML 里手写一条"关闭"都写不出来。

所以凡**会被回放打开的窗口**（对话框、浮动面板），都得像设置对话框的
`settingsCloseButton` 那样给一个应用内的关闭入口，否则它在脚本里"只进不出"：
录制时无声无息（X 录不到），回放时窗口一直挂着，后面的事件全在错误的前提下跑。

### 放慢回放

默认每条事件之间等 100 ms（编译期量 `QT_TESTING_EVENT_PLAYBACK_DELAY`），
十几条事件的脚本三四秒就跑完了，人眼跟不上。加 `--slow` 放慢——它只影响看着跑
的场景，给 CI 跑不要加：

```bat
build\ninja-relwithdebinfo-x64\bin\demo_app.exe --play sb.xml --slow 500
```

**不要往脚本里插 `pause` 事件。** 库确实有个 `pause` 命令，但它的实现是
`SleeperThread::msleep`，头文件原话是 "no events will be processed and the
application will appear frozen"——等待期间界面**冻住**，比默认的飞快还难看；
而且往脚本里插延时意味着要维护第二份文件，录制内容一改就得重生成。

`--slow` 走的是 `pqEventDispatcher::setEventPlaybackDelay()`（公开的静态 setter），
内部用 `processEventsAndWait`，等待期间照常处理事件，界面正常刷新。三条路对比：

| 做法 | 等待期间界面 | 要不要第二份脚本 | 要不要改编译 |
| ---- | ------------ | ---------------- | ------------ |
| 脚本里插 `pause` | **冻住** | 要 | 不要 |
| 改 `QT_TESTING_EVENT_PLAYBACK_DELAY` | 正常 | 不要 | **要** |
| `--slow`（= `setEventPlaybackDelay`） | 正常 | 不要 | 不要 |

顺带一条：`pause` 和 `process_events` 这类**"对象无关"**的命令，事件里的 `widget`
属性仍会被解析一遍——路径不存在一样会在查对象阶段报错返回。真要手写这类事件，
挂一个当时确实存在的控件路径。

## 扩展指引

**新增一个模块**：在 `src/` 下建目录并写 `CMakeLists.txt`

```cmake
set(TARGET_NAME ${APP_TARGET_PREFIX}_xxx)
add_library(${TARGET_NAME} STATIC ${SRCS})
target_include_directories(${TARGET_NAME} PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
```

再在 `src/CMakeLists.txt` 中 `add_subdirectory(xxx)`，按需在 `app` 里链接。

**新增一个通用控件**：放进 `qt-libui` 仓库的 `src/` 下，只依赖
`Qt5::Widgets`，并在该仓 `examples/gallery/` 里加演示页。若需样式，用
`setObjectName` 并在本仓 `src/app/resources/styles/default.qss` 中以
`#objectName` 选择器定义，不在 C++ 里硬编码 `setStyleSheet`。

**新增一个设置页**：在 `src/app/dialogs/settings_dialog.cpp` 中写一个
`createXxxPage()`，再经 `addCategoryPage("分组名", page)` 注册，即自动
出现在左侧分类导航中。控件用 `addSpinBoxRow` / `addComboBoxRow` /
`addCheckBoxRow` 创建，它们会即时写回 `ConfigManager`。

**新增第三方库**：压缩包放入 `3rdparty/` 并在 `cmake/extract_dependencies.cmake`
的 `DEPENDENCY_ARCHIVES` 中登记（首次 configure 时自动解压），再在顶层
`CMakeLists.txt` 中 `add_subdirectory`。

**新增一个入库即执行的 `.sh`**（如 `scripts/build_ninja.sh`）：在 Windows 上
`git add` 记下的是 644，因为 `core.fileMode` 在 Windows 上为 false——git 不
记录可执行位，改文件系统权限也没用，只能直接改索引：

```bash
git update-index --chmod=+x scripts/xxx.sh
```

这个坑本地测不出来：`bash script.sh` 能跑、先手工 `chmod +x` 能跑、拷到别处
也能跑，只有**从零克隆到 Linux 再 `./script.sh`** 才报 `Permission denied`
（退出码 126）。所以判定标准不是「本地跑得通」，而是从零克隆跑得通——`.sh`
的改动建议真的克隆一份验证。

`.sh.in` 模板反之要保持 644：生成出来的脚本由 `file(CHMOD)` 或
`configure_run_script` 补位，模板自己带执行位没有意义。

## Linux 构建

前置条件：CMake ≥ 3.19，以及 `find_package` 所需组件的开发包：

```bash
sudo apt install qtbase5-dev libqt5svg5-dev \
    libqt5serialport5-dev libqt5opengl5-dev
```

Ubuntu 20.04（focal）自带的 CMake 是 3.16，低于本工程的下限，需要另装
（3.26 以上更好，`.vscode/tasks.json` 里的预设任务要 version 8 的
CMakePresets）。两种装法：

```bash
# 其一：Kitware 官方源
wget -O - https://apt.kitware.com/keys/kitware-archive-latest.asc 2>/dev/null \
    | gpg --dearmor - | sudo tee /usr/share/keyrings/kitware-archive-keyring.gpg >/dev/null
echo 'deb [signed-by=/usr/share/keyrings/kitware-archive-keyring.gpg] https://apt.kitware.com/ubuntu/ focal main' \
    | sudo tee /etc/apt/sources.list.d/kitware.list >/dev/null
sudo apt update && sudo apt install cmake

# 其二：官方二进制包，解到 ~/.local，不需要 sudo
mkdir -p ~/.local && cd /tmp
wget https://cmake.org/files/v3.31/cmake-3.31.6-linux-x86_64.tar.gz
tar xf cmake-3.31.6-linux-x86_64.tar.gz -C ~/.local
# 写进 ~/.profile 而非 ~/.bashrc：后者只被交互式 shell 读，IDE 的任务、
# `wsl bash -c` 这类非交互调用都看不到，会退回系统那份旧 cmake
echo 'export PATH=$HOME/.local/cmake-3.31.6-linux-x86_64/bin:$PATH' >> ~/.profile
```

```bash
# 配置 + 构建 + 测试，一条龙
scripts/build_ninja.sh -t debug
ctest --test-dir build/linux-ninja-debug --output-on-failure
```

脚本不走 CMakePresets（那套是给 MSVC 的：预设名带 x64/x86、cache 里有
`CMAKE_MSVC_RUNTIME_LIBRARY`，而 `binaryDir` 恰好就是 `build/ninja-<类型>-<架构>`
——与 Windows 侧同名）。在 WSL 等共享同一棵源码树的场景下，用预设会直接
覆盖 Windows 侧的 CMakeCache。脚本因此改用独立目录
`build/linux-ninja-<类型>`，两边互不相干。

- Linux 不读取 `local.cmake`，Qt 由系统路径解析；必要时用
  `-DCMAKE_PREFIX_PATH` 指定 Qt 安装位置
- `qt-libui` 随 submodule 一起构建，不需要单独安装，也没有额外的路径要配
- 运行脚本由 `configure_run_script` 生成，Windows 出 `.bat`、Linux 出
  `.sh`（自动加可执行权限）
- Windows 的部署与打包（windeployqt / Inno Setup）仍为 Windows 专属；
  Linux 侧的打包见下节

## Linux 打包（AppImage）

产出单一可执行文件，内含 Qt 运行库与平台插件，目标机器无需安装 Qt。

```bash
scripts/build_ninja.sh -t relwithdebinfo -p
```

产物落在 `dist/`：

- `<应用名>-<架构>-<版本>.AppImage`
- `symbols/<版本>-<git短hash>-<架构>/<目标名>`：**未 strip** 的可执行文件。
  AppImage 内的二进制经过 strip，崩溃日志里只有裸地址，事后要用这份归档
  才能解析调用栈：`addr2line -e <归档的二进制> -f -C <地址>`。对应 Windows
  侧的 exe + PDB 归档

其他要点：

- **打包工具与 type2 runtime 随仓库提供**（`3rdparty/appimage-tools/`，约
  47 MiB），打包全程不联网。之所以入库而不按需下载：国内网络下 GitHub 的
  release 资源 CDN 常常不可达，按需下载会让打包直接失败——早先漏了
  `runtime-x86_64`，结果是 `appimagetool` 挂在一个没有超时的下载上（日志末行
  `Downloading runtime file from ...`，进程 CPU 为 0，看着像在压缩）。详见该
  目录下的 README
- 直接用 `scripts/make_appimage.sh <bin 目录>` 也可（该脚本由 CMake 生成，不要
  手改模板以外的内容）。参数是可执行文件所在目录，如
  `build/linux-ninja-relwithdebinfo/bin`：脚本落在源码树、被所有构建目录共用，
  后 configure 的会覆盖先前的，不比对这个参数就可能执行到别人的脚本（轻则
  找不到二进制，重则连 Debug 的打包拦截一起绕过）。构建配置校验也在脚本内，
  直接调用同样拦得住 Debug
- **Qt 由 configure 时定位到的 qmake 注入**，保证打进 AppImage 的 Qt 与工程
  链接的是同一套。要改用别的 Qt，导出 `QMAKE` 覆盖：
  `QMAKE=/opt/Qt/5.15.2/gcc_64/bin/qmake ./scripts/make_appimage.sh build/linux-ninja-relwithdebinfo/bin`
- 工具按架构命名（`<工具>-<架构>.AppImage`），仓库里现装的是 **x86_64** 一套。
  构建目标架构与之不符时，脚本会明确指出缺哪个文件，而不是打出一个跑不起来的包
- 拒绝 Debug 配置打包，理由与 Windows 侧不同，日志会给出具体命令
- 打包需要 `strip`（binutils，通常随 build-essential 一起装上）
- AppImage 的图标与桌面项取自 `APP_APP_NAME` / `APP_URL`，与安装包同源；
  `cmake/appimage.desktop.in` 中可加 `Comment=` 等字段

## 发布

发布一律使用 `relwithdebinfo` 配置，并连同符号一并归档：

```bash
scripts/build_ninja.bat -t relwithdebinfo -p
```

## 编辑器配置

`.vscode/` 随仓库提供，克隆后即可使用：

- `settings.json` — 唯一需要按机器调整的是 `qtcmake.qtDir`（见必改项 4）与
  `clang-format.executable`；`fallbackStyle` 已按项目约定设为 `Google`
- `launch.json` — 调试 `demo_app` 与崩溃测试两个配置，Qt 路径经
  `${config:qtcmake.qtDir}` 引用，无需重复填写
- `tasks.json` — 配置 / 构建 / 测试三个 CMake 任务（preset 见
  `CMakePresets.json`），另有发布打包任务
- `extensions.json` — 推荐扩展清单

若需放本机私有配置而不入库，可用 `.vscode/settings.local.json` 之类的个人文件。

另有两个配置由 CMake 生成或随仓库提供：

- **`.clangd`**（生成，不入库）—— 由 `cmake/.clangd.in` 在 configure 时生成，
  把 clangd 指向本次配置的构建目录。本项目构建目录按 preset 分开，clangd
  无法自动找到 `compile_commands.json`，不加此文件会把所有 Qt 头判为
  「file not found」
- **`.clang-format`**（入库）—— 基于 Google 风格，见上方"代码风格"相关约定。
  用法：`clang-format -i <file>`，或 `clang-format --dry-run --Werror <file>`
  做检查
