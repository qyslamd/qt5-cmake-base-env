# 构建配置与崩溃排查

崩溃捕获本身是运行时机制，与构建配置无关：**两侧、任何配置都能捕获崩溃并落盘
日志**。构建配置只影响一件事——事后能不能把日志里的地址还原成函数名与行号。

两侧的"符号"载体不同：Windows 是独立的 PDB 文件，Linux 是可执行文件里的
DWARF 与符号表，所以 Linux 侧归档的就是**未 strip 的可执行文件本身**。

## 平台总览

| 项目 | Windows | Linux |
|------|---------|-------|
| 捕获机制 | 向量化异常处理 + 未处理异常过滤器 | `sigaction` + `sigaltstack` + `backtrace` |
| 覆盖范围 | 访问违规、除零、`abort()` 等 | SIGSEGV / SIGABRT / SIGFPE / SIGILL / SIGBUS |
| 崩溃日志名 | `crash_yyyyMMdd_HHmmss.log` | `crash_<Unix 时间戳>.log` |
| 转储文件 | minidump（`.dmp`） | 无 |
| 日志目录 | `%LOCALAPPDATA%\<组织名>\<应用名>\crash\` | `~/.local/share/<组织名>/<应用名>/crash/` |
| 崩溃时交互 | 有 `QApplication` 时弹 MessageBox | 只往 stderr 打三行，无弹窗 |
| 事后解析 | WinDbg + 归档的 PDB | `addr2line` + 归档的未 strip 可执行文件 |
| 归档产物 | `dist/symbols/<版本>-<git 短 hash>-<架构>/` 下的 exe 与 pdb | 同目录规则下的可执行文件 |

## 发布约定

**两侧一律使用 `relwithdebinfo` 配置**，不要用 `release`：

```bash
scripts/build_ninja.bat -t relwithdebinfo -p     # Windows：安装包
scripts/build_ninja.sh  -t relwithdebinfo -p     # Linux：AppImage
```

原因见下文两侧各自的「各配置」小节：Release 在 Windows 上不产 PDB、在 Linux
上不带 `-g`，崩溃日志里的地址将无法还原成函数名与行号，排查成本极高。

每次发布的二进制与**对应的符号必须一并归档**。崩溃日志与转储里记录的都是
地址，事后解析要拿崩溃那一刻那个二进制匹配的符号——Windows 是 PDB，Linux 是
未 strip 的可执行文件。

## 客户回传的崩溃报告

发布给客户（离线）的程序崩溃后，客户不会自己去数据目录里翻文件，所以程序会在
**下次启动**时提示导出：弹出「上次运行发生过崩溃」，点「导出报告」即可把报告
导出到桌面 `CrashReport-<时间戳>/`，客户把这个文件夹发回来即可。

三种导出方式，产物一致（`<uuid>.dmp` + `summary.txt`）：

| 方式 | 用法 | 场景 |
|------|------|------|
| 启动提示（推荐） | 启动时自动弹出，点「导出报告」 | 客户正常使用 |
| 安装目录下的脚本 | 双击 `export_crash_report.bat` | 客户没看到提示，或程序起不来 |
| 命令行 | `demo_app --export-report [--export-dir <目录>]` | 售后远程指导、CI 与演练 |

`summary.txt` 是给人看的：应用名、版本、git 提交、构建配置、平台、崩溃时间、
报告文件名与大小。开发者凭版本与 git 提交，去
`dist/symbols/<版本>-<git 提交>-<架构>/` 取对应符号。

崩溃报告落在哪（数据库目录）：

| 平台 | 待处理（尚未交给开发者） | 交付后 |
|------|--------------------------|--------|
| Windows | `%LOCALAPPDATA%\<组织名>\<应用名>\crash\reports\` | 仍在 `reports\`，元数据标记为已交付 |
| Linux | `~/.local/share/<组织名>/<应用名>/crash/pending/` | 移到 `completed/` |

导出**不删除**报告，只转入已交付状态：客户把导出目录弄丢时还能再导一次，程序也
不会再提示同一份报告。

### 开发机上恢复堆栈

Windows（`cdb` 或 Visual Studio 直接打开 dmp）：

```bat
cdb -z <uuid>.dmp -y <bin 目录或归档符号目录> -c ".ecxr; .lines; kn 8; q"
```

Linux（lldb 直接读 minidump，不需要转符号文件；命令与参数顺序的坑见
[Linux：用 lldb 解析 minidump](#linux用-lldb-解析-minidump)）：

```bash
lldb -b -o "bt" -o "quit" -c <uuid>.dmp <未 strip 的 demo_app> < /dev/null
```

两侧都能给出「函数名 + 文件:行」。实测（两平台各跑一遍 `--crash` 触发的空指针写）：

```text
# Windows（cdb + PDB）
00 demo_app!`anonymous namespace'::TriggerTestCrash [main.cpp @ 204]
01 demo_app!main+0x6a9 [main.cpp @ 442]

# Linux（lldb + DWARF）
frame #0: demo_app`main at main.cpp:206:17
```

### 报告里有什么、没什么

minidump 含：线程栈、寄存器、模块列表（Windows 是 PDB 签名，Linux 是 ELF
build id）与注解。**不含**全局变量与堆对象内容——Crashpad 固定写
`MiniDumpNormal`，且 Linux 上 extra memory ranges 与间接引用内存都是空实现。
要看具体变量的值，能依靠的是：栈上的局部变量（未被优化掉的）、`summary.txt`
里的构建信息，以及业务侧主动写进崩溃注解的状态。

## Windows：各配置下的崩溃捕获能力

崩溃捕获依赖 `AddVectoredExceptionHandler` 与
`SetUnhandledExceptionFilter`，属运行时机制，`WindowsCrashHandler.cpp`
中也没有条件编译。**四个配置都能捕获崩溃**，日志与 minidump 都会写；
差别只在崩溃日志中栈回溯的**符号可读性**。

以下为实际构建并触发访问违规后的实测结果：

| 配置 | 编译标志 | 链接 `/debug` | 产出 PDB | 崩溃日志中的调用栈 |
|------|----------|:---:|:---:|--------------------|
| `debug` | `/Zi /Ob0 /Od /RTC1` | 是 | 是 | 函数名 + 文件:行 |
| `relwithdebinfo` | `/Zi /O2 /Ob1 /DNDEBUG` | 是 | 是 | 函数名 + 文件:行 |
| `release` | `/O2 /Ob2 /DNDEBUG` | 否 | 否 | `0x0091282a [未知函数]` |

`relwithdebinfo` 与 `debug` 的栈形如：

```text
 0: 0x00405019 RunCrashChild() D:\...\crashhandler_test.cpp:61
 1: 0x00409557 main()          D:\...\crashhandler_test.cpp:242
 2: 0x0046d896 __scrt_common_main_seh() ...\exe_common.inl:288
 3: 0x756a5d49 BaseThreadInitThunk()
```

`release` 的同一处形如：

```text
 0: 0x0091282a [未知函数]
 1: 0x00914f72 [未知函数]
 2: 0x0093fdcb [未知函数]
 3: 0x756a5d49 BaseThreadInitThunk()
```

Release 下系统 DLL 的帧仍能解析（它们有导出符号），只有本工程的帧因
缺少 PDB 而丢失名称。栈的帧数本身是完整的，只是没有符号。

### 帧指针省略不影响栈回溯

`/O2` 在 x86 上隐含 `/Oy`（省略帧指针），理论上会破坏 `StackWalk64`。
实测未发生：x64 的 PE 始终携带 unwind 信息；x86 在 `release` 下同样
走全了 6 帧。故该项不构成配置选择的依据。

## Windows：符号（PDB）管理

### 归档位置

`make_package` 依赖 `make_symbols`，打包前自动把可执行文件与 PDB 复制到
带版本号与架构的目录：

```text
dist/
├── QtCMakeAppDemo-setup-x86-1.0.0.42.exe
└── symbols/
    └── 1.0.0.42-9ab3f10-x86/
        ├── demo_app.exe
        └── demo_app.pdb
```

也可单独执行归档：

```bash
cmake --build build/ninja-relwithdebinfo-x86 --target make_symbols
```

### 为什么必须归档

两个独立的原因，任何一个都足以让未归档的符号永久失效：

1. **exe 内嵌的是构建机的绝对路径**。实测
   `demo_app.exe` 中记录的 PDB 路径为
   `D:\sb\...\build\ninja-relwithdebinfo-x86\bin\demo_app.pdb`，
   分析机上该路径不存在，WinDbg **不会**自动找到符号。
2. **同一版本号可以对应不同的二进制**。版本号由 git 派生（最近的 tag 提供
   前三段、提交总数提供 build 号），工作区有未提交改动时版本号不变，但产出的
   exe 与 PDB 与干净构建不同；只按版本号归档，脏构建会覆盖掉发布构建的符号。
   故归档目录名除版本号外还带 git 短 hash。

### release 配置下的行为

`release` 不产 PDB，此时归档脚本只复制 exe 并给出告警，**不会中断打包**：

```text
CMake Warning at cmake/archive_symbols.cmake:29 (message):
  未找到符号文件（.../demo_app.pdb），本次不归档符号。
  该配置未启用调试信息，其崩溃转储将无法解析调用栈；
  发布请使用 relwithdebinfo 配置。
```

### 使用归档的符号解析转储

拿到用户的 `crash_*.dmp` 后，把符号路径指向对应的归档目录：

```text
windbg -z crash_20260911_170559.dmp

.sympath+ D:\release\symbols\1.0.0.42-9ab3f10-x86
.reload /f
!analyze -v
kb
```

`.sympath+` 追加而非覆盖，因此依然会从 Microsoft 符号服务器解析系统帧。

### 安装包不携带 PDB

`.iss` 中没有 PDB 条目，已确认安装包不会带上它。原因：单个 PDB 达
16 MB，且会暴露内部符号信息，而客户机没有解析转储的需求。符号留在
发布方一侧即可。

### 备选：符号服务器

版本多、发布频繁时，可用 `symstore.exe`（随 Windows SDK 提供）把符号
归入统一目录，或搭建符号服务器：

```bat
symstore add /r /f dist\symbols\1.0.0.42-9ab3f10-x86\*.pdb ^
    /s D:\symbols /t "demoapp" /v "1.0.0.42"
```

随后把 `.sympath` 指向 `D:\symbols` 即可，无需按版本切换路径。本项目
模板默认采用上一节的按版本目录归档，够用且无需额外工具。

## Linux：崩溃捕获

`LinuxCrashHandler` 用 `sigaction` 注册 SIGSEGV / SIGABRT / SIGFPE / SIGILL /
SIGBUS，标志为 `SA_SIGINFO | SA_ONSTACK | SA_RESETHAND`，并预先分配一块
`SIGSTKSZ` 的备用栈——崩溃把当前栈打得不可用时（如栈溢出）仍有一条能用的栈。
信号处理器内零堆分配，只用固定缓冲加 `backtrace_symbols_fd` 写 fd。

三处与 Windows 的实质差异：

- **没有转储**，只有日志。Linux 侧不产 minidump，可解析的信息就是日志里的栈。
- **回调不执行、不弹窗**。`setCrashCallback` 的实参在 Linux 上不会被调用
  （`std::function` 不满足 async-signal-safe 约束），崩溃时只往 stderr 打：

  ```text
  程序崩溃 (SIGSEGV)
  崩溃日志已写入: /home/zhou/.local/share/Enpht/QtCMakeAppDemo/crash/crash_1790071576.log
  使用 addr2line 解析调用栈地址。
  ```

- **退出码是 `128 + 信号号`**：实测 SIGSEGV 139、SIGFPE 136、SIGABRT 134。
  CI 里据此区分崩溃与断言失败即可，无需解析日志。

日志写在 `AppLocalDataLocation/crash/`，文件名是
`crash_<Unix 时间戳（秒）>.log`——注意与 Windows 的
`crash_20260922_180612.log` 格式不同，两侧脚本不要共用一个解析规则。
内容实例如下（实测，省略了系统信息与程序信息两段）：

```text
=== 崩溃信息 ===
信号: SIGSEGV (11)
si_code: 1
故障地址: (nil)

=== 调用栈 (6 帧) ===
build/linux-ninja-relwithdebinfo/bin/tests/test_core_crashhandler(+0x68fad)[0x5b1ef715bfad]
build/linux-ninja-relwithdebinfo/bin/tests/test_core_crashhandler(+0x69210)[0x5b1ef715c210]
/lib/x86_64-linux-gnu/libpthread.so.0(+0x14420)[0x76279532c420]
build/linux-ninja-relwithdebinfo/bin/tests/test_core_crashhandler(+0x244ab)[0x5b1ef71174ab]
/lib/x86_64-linux-gnu/libc.so.6(__libc_start_main+0xf3)[0x762794850083]
build/linux-ninja-relwithdebinfo/bin/tests/test_core_crashhandler(+0x24b4e)[0x5b1ef7117b4e]
```

系统库的帧自带函数名（它们有导出符号），本工程的帧只有 `(+0x…)` 偏移——
链接没有加 `-rdynamic`，本工程的符号不在动态符号表里。这不是缺陷：偏移配上
带 DWARF 的二进制即可还原，见下节。

## Linux：各配置下的解析能力

| 配置 | 编译标志 | 崩溃日志 | `addr2line` 能还原出 |
|------|----------|:---:|----------------------|
| `debug` | `-g` | 照写 | 函数名 + 文件:行 |
| `relwithdebinfo` | `-O2 -g -DNDEBUG` | 照写 | 函数名 + 文件:行 |
| `release` | `-O3 -DNDEBUG` | 照写 | 函数名，无文件:行 |

`relwithdebinfo` 与 `release` 两行是在 WSL 上真实触发崩溃后实测的（后者另建了
`build/linux-ninja-release`）；`debug` 与 `relwithdebinfo` 只差优化级别、用的是
同一份 DWARF，故并入同一结论。三者印证的是同一件事——**崩溃日志本身不缺信息，
缺的只是事后解析用的那份二进制**。

回溯不依赖帧指针：glibc 的 `backtrace()` 走的是 libgcc 的展开表，实测 `-O2`
（GCC 默认省略帧指针）下六帧齐全，故与 Windows 侧一样，该项不构成配置选择
的依据。

## Linux：符号与发布裁剪

AppImage 打包会 `strip --strip-unneeded` 包内的可执行文件（`cmake/`
`make_appimage.sh.in`），随后把**未 strip 的那一份**复制到符号目录——这是
`make_appimage` 的最后一步，对应 Windows 侧的 `make_symbols`：

```text
dist/
├── QtCMakeAppDemo-x86_64-1.0.0.42.AppImage          ← 分发给用户
└── symbols/
    └── 1.0.0.42-9ab3f10-x64/
        └── demo_app                                  ← 自留，勿分发
```

目录名与 Windows 侧同规则（版本号 + git 短 hash + 架构）。**两条路径的架构写法
不同**：符号目录用 `APP_ARCH_SUFFIX`（`x64`），AppImage 文件名用 `APPIMAGE_ARCH`
（`x86_64`），脚本里不要拿其中一个去匹配另一个。Linux 没有独立的符号文件，
归档的就是可执行文件本身，所以它**同时是可运行的程序**——别把它当成"只是符号"
而随手删掉。

Debug 配置下打包会被拒绝（`cmake/check_package_config.cmake`），理由与
Windows 不同：Linux 侧不是运行时缺失，而是产物体积大、带断言开销，且 AppImage
反正要 strip 掉调试信息。非 `relwithdebinfo` 的其它配置只告警不拦截。

### 用归档的二进制解析崩溃日志

**取圆括号里的 `+0x…` 偏移，不要取方括号里的地址。** 二进制是 PIE
（`readelf -h` 显示 `Type: DYN`），方括号里是运行时的绝对地址（加载基址 +
偏移），直接喂给 `addr2line` 只会得到 `??`。下例取自崩溃测试二进制：

```bash
# 正确：用 +0x68fad
addr2line -e dist/symbols/1.0.0.42-9ab3f10-x64/demo_app -f -C 0x68fad
LinuxCrashHandler::doCrashDump(int, siginfo_t*)
/home/zhou/works/qt-cmake-base-env/src/core/crashhandler/linux_crash_handler.cpp:208

# 错误：方括号里的绝对地址
addr2line -e ... 0x5b1ef715bfad
??
??:0
```

同一处崩溃在三类二进制上的实测差别，说明了为什么**必须用归档的那一份**：

| 手上的二进制 | 解析结果 |
|--------------|----------|
| 归档的未 strip 产物 | `LinuxCrashHandler::doCrashDump(int, siginfo_t*)` + `linux_crash_handler.cpp:208` |
| `release` 配置的产物（无 `-g`） | 函数名正确，但只有 `??:?` |
| AppImage 内那份（`strip --strip-unneeded`） | 名字是**错的**，给了一个毫不相干的 `std::__cxx11::basic_string<...>::_M_construct` |

第三行值得留意：strip 过的二进制不是"少给点信息"，而是会**给出错误的函数名**
——符号表没了，`addr2line` 只能退回最近的可疑符号。用包里的二进制排查，结论
会比没有结论更糟。

每行的崩溃都由对应二进制自己触发，**偏移不可互换**：把 `release` 那个偏移喂给
`relwithdebinfo` 的二进制，得到的是另一个函数。这正是"归档要与那个二进制配对"
的由来。

### 备选：`-rdynamic` 让崩溃日志自带符号名

给链接选项加 `-rdynamic`（即 `-Wl,--export-dynamic`），本工程的符号会进动态
符号表，`backtrace_symbols_fd` 便能打出函数名。实测同一段调用栈：

```text
不加：  ./bt(+0x11f1)[0x5ec099fd81f1]
加：    ./bt(_Z6Level2v+0x31)[0x5d0d5a8121f1]
```

代价是动态符号表变大、内部符号外露，且给出的仍是 mangled 名、依然没有文件:行
（那要 DWARF）。本模板默认不加：偏移 + 归档二进制这条路已经足够，且发布体积
更小。

## Linux：用 lldb 解析 minidump

回传的 minidump 在 Linux 侧用 **lldb** 解析，理由有两条：

- **gdb 读不了 minidump**。实测 Ubuntu 20.04 的 gdb 9.2 二进制里没有任何
  minidump 相关符号（`strings /usr/bin/gdb | grep -ci minidump` 得 0），
  `gdb -c x.dmp` 走不通。要落到 gdb 上，得先用 breakpad 的 `minidump-2-core`
  把 dump 转成 core 文件。
- **lldb 自带 minidump 解析**（`ObjectFileMinidump` / `ProcessMinidump` 插件），
  直接读未 strip ELF 里的 DWARF，不需要 `dump_syms` + `minidump-stackwalk`
  那一套符号文件流水线。

安装（Ubuntu 20.04 仓库里是 lldb 10）：

```bash
sudo apt install lldb
```

### 命令与参数顺序（这里有个坑）

```bash
cd build/linux-ninja-relwithdebinfo/bin      # 未 strip 的可执行文件所在目录
lldb -b -o "bt" -o "quit" -c <uuid>.dmp ./demo_app < /dev/null
```

- `-c` 是 `--core` 的别名：lldb 把 minidump 当 core 文件读。
- `-b`（batch）不进入交互模式，`-o "<命令>"` 按顺序执行命令。
- **选项必须写在可执行文件之前**。写成
  `lldb -c <uuid>.dmp ./demo_app -o "bt"` 时，lldb 会把 `-o` 及其后的内容当成
  **被调试程序的参数**，一条命令都不执行，进程停在 `(lldb)` 提示符等输入。
  无人值守时表现为"卡死"：实测挂满 300 秒、零输出。
- 末尾 `< /dev/null` 是保险：万一 lldb 仍要读 stdin，给它 EOF，而不是挂在管道上
  等（加不加 `-o "quit"` 都对，两条一起更稳）。

### 常用命令

| 命令 | 用途 |
|------|------|
| `bt` | 崩溃线程的调用栈（带文件:行） |
| `bt all` | 所有线程的栈，卡死/死锁时用 |
| `frame select 2` 再 `frame variable` | 切到某一帧看局部变量 |
| `image list` | 模块与 build id，用来核对是否与归档的二进制一致 |
| `target modules add <ELF>` | 把本地文件挂到 dump 里只显示模块名的项上 |

模块路径取的是 dump 里记录的**构建机绝对路径**。换了机器（或构建目录被删）时，
`image list` 里那些模块会显示成裸名字，用 `target modules add` 把归档的未 strip
ELF 挂上即可——符号（DWARF）就在那个 ELF 里，不需要额外文件。

### 只显示一帧不等于解析失败

演示用的崩溃点会被编译器内联（`--crash` 触发的那个 `TriggerTestCrash` 就被 GCC
内联进了 `main`），而 `main` 之上就是 libc 启动代码——那里没有可展开的信息，所以
栈只有一帧是正常的。业务代码里的多层调用链能完整展开，用同一条 crashpad 链路、
同样的 `-O2`（**未加**帧指针）做的隔离实验实测：

```text
frame #0: Level3() at fp_test.cpp:18:17
frame #1: Level2() at fp_test.cpp:20:49
frame #2: Level1() at fp_test.cpp:21:49
frame #3: main at fp_test.cpp:50:9
```

结论：Linux 侧不依赖帧指针，**不必**为它加 `-fno-omit-frame-pointer`。

## 工具链随仓库提供：cmake / ninja / clang

Windows 侧只需要装两样东西：**Qt 与 VS2019**（外加 Windows SDK，随 VS 装）。
其余构建工具都随仓库提供，版本由仓库定死，不随各人机器上装了什么而变：

| 工具 | 位置 | 版本 | 谁在用 |
|------|------|------|--------|
| ninja | `3rdparty/ninja.exe` | 1.10.2 | 预设与 `build_ninja.bat` |
| cmake | `3rdparty/cmake/bin/` | 4.2.0 | 同上（与同版本 `share/` 成套） |
| clang-format / clang-tidy / clangd | `3rdparty/clang/` | 21.1.2 | `scripts/clang_format.bat`、`scripts/clang_tidy.bat`、编辑器 |
| 7z / Inno Setup 6 / Python 3.8.8 / cloc | `3rdparty/` | — | 解压、打包、funq、代码统计 |

### 为什么固定版本

- **ninja**：VS2019 各版本安装自带的 ninja 版本不同，有的仍是 **1.8.2**。
  本项目要求 ninja ≥ 1.10.0，所以不用 VS 那份，固定用仓库自带的。
- **clang-format**：排版结果随版本变。各人用各自装的那份，diff 里就会混进
  纯格式噪声（与 `CLAUDE.md` 规则 20 是同一条约定）。

### 各入口怎么用到它们

- `CMakePresets.json` 的每个预设都有
  `"CMAKE_MAKE_PROGRAM": "${sourceDir}/3rdparty/ninja.exe"`；
  `scripts/build_ninja.bat` 用 `3rdparty/cmake/bin/cmake.exe`（找不到才退回
  PATH 上的 cmake），并在开跑前检查 ninja 在不在。
- 顶层 `CMakeLists.txt` 有一道**版本闸门**：生成器是 Ninja 时执行
  `<ninja> --version`，低于 1.10.0 或跑不起来就 `FATAL_ERROR`。
  它挡的是绕过预设的配置，主要是**既有构建目录**——`CMAKE_MAKE_PROGRAM`
  是缓存变量，预设里新写的值不会自动覆盖旧的（同 `CLAUDE.md` 规则 18）。
  出现这个报错时清掉那条缓存项即可：

  ```bash
  cmake -B build/ninja-relwithdebinfo-x86 -U CMAKE_MAKE_PROGRAM
  ```

- clang-tidy / clang-format 也是**自带的那份一路优先**：CMake 里直接写死
  `3rdparty/clang/...`（不走 `find_program` 的缓存，免得既有构建目录一直用着
  第一次找到的别的版本），只有自带那份不在时才去搜 PATH。
- `.vscode/settings.json` 把 clang-format、clangd 与 CMake Tools 都指向
  `3rdparty/` 下，编辑器里跑的与命令行跑的、别人跑的是同一份。

### Linux 侧不适用

`3rdparty/` 里这些是 Windows 可执行文件，WSL / Linux 用不了：
`build_ninja.sh` 仍用系统装的 cmake 与 ninja（`apt install cmake ninja-build`），
clang 工具也用系统那份。Linux 侧的前置条件见[模板使用指南](模板使用指南.md)。

## Ninja 依赖日志空了：改了头文件却不重编

**症状**：改了一个**只在头文件里**的东西（加个成员、改个声明），
`cmake --build` 只重编了一两个 `.cpp` 就报成功；跑测试时**访问违例**
（`0xc0000005`），或者行为诡异。

**看起来像代码 bug，其实是构建的问题。**

### 根因

MSVC + Ninja 下唯一记录"谁 include 了谁"的地方是 `.ninja_deps` 依赖日志
（编译规则用 `deps = msvc` + `/showIncludes`；`build.ninja` 里**没有**任何
头文件的 input 边——往 `CMakeLists.txt` 的 target 里补头文件名**不管用**，
那只影响 IDE 工程生成）。

这个日志**偶发**会把某些 TU 的依赖记成**空**，而记录本身带有效 mtime，
于是 ninja 认为"这条依赖是新鲜的、就是没有依赖"——**头文件改了它不会重编**。
两个 TU 之间布局不一致（例如某个类多了一个成员，而另一个 TU 还按旧布局编），
链接不会报错，运行时就炸。

### 怎么确认

```bash
cd build/ninja-relwithdebinfo-x86
ninja -t deps src/app/CMakeFiles/demo_app.dir/main.cpp.obj
```

正常会列出上百条头文件。**`#deps 0` 就是中招了**——把你手上那个出问题的
TU 的对象路径换进去（`ninja -t deps` 对任何 `.obj` 都能问）。

### 怎么办

删掉相关对象的 `.obj` 再重编——**光"强制重编"不够**：如果只是 `touch` 源文件
让 ninja 重跑编译，它**可能又记成空**（实测：一次强制重编之后，同一个 TU 的
条目又变回 `#deps 0`）。必须删文件：

```bash
rm build/ninja-relwithdebinfo-x86/src/<模块>/CMakeFiles/<target>.dir/*.obj
scripts\build_ninja.bat -t relwithdebinfo -a x86
```

再按上面的 `ninja -t deps` 复核一遍，**确认条目非空**才算修好。

**重编必须走 `scripts\build_ninja.bat`，不要直接在 Git Bash 里敲
`cmake --build`。** 实测：同样删掉那几个坏对象，直接 `cmake --build` 重编回来
的**又是 `#deps 0`**，而走脚本重编就正常。怀疑是控制台代码页不匹配，让 ninja
认不出本地化过的 `/showIncludes` 前缀（`msvc_deps_prefix = 注意: 包含文件:`，
见 `CMakeFiles/rules.ninja`）。**也就是说"删了重编"这个修法本身取决于你怎么
调 ninja**——复核那一步不能省。

**修好的样子**：`touch` 某个被 include 的头文件之后，`ninja -n <target>` 会把
依赖它的 TU **连同测试对象**都列为待重建；全量扫一遍 `ninja -t deps`，
**手写源码里没有 `#deps 0`**（只剩生成物：`qrc_*`、`mocs_compilation`、
`.rc.res`、`.asm.obj`——**那几个是正常的，不用管**）。

### 判据

**改了头文件之后，不要凭"ninja 说要编几个文件"判断**——它在这个状态下会撒谎。
要么看一眼 `ninja -t deps`，要么把对应的 `.cpp` 一并动一下触发重编，
要么直接删对象重编。

## 开关从 OFF 切回 ON 之后链接报未解析符号

**症状**：把某个开关关掉再打开（实测 `APP_ENABLE_AUTH`），重新 configure 之后
链接报 `AuthService::staticMetaObject` 或 `loginSucceeded` 未解析——而定义那个
类的源文件明明在源列表里。

**根因**：开关 OFF 期间那些源没进编译，AUTOMOC 也就没为它们生成 moc。切回 ON
后 `<构建目录>/src/<模块>/<target>_autogen/mocs_compilation.cpp` 不会因为源文件
重新入列而重生成，里面始终缺那一行 include。

**怎么办**：删掉那个 `<target>_autogen` 目录再构建，或者换个干净的构建目录。

**判据**：报未解析的符号以 `staticMetaObject` 或信号名结尾，而类的 `.cpp` 确实
在源列表里——先看 autogen 目录，不要先怀疑代码。

## 备选：让 release 也产 PDB

若因性能原因确需用 release 发布，可为其补上调试信息：

- 在 preset 中设置
  `CMAKE_MSVC_DEBUG_INFORMATION_FORMAT:STRING=ProgramDatabase`
  （CMake 3.25+，policy CMP0141 生效时自动补 `/Zi` 与 `/DEBUG`）
- 或直接给 Release 的编译标志加 `/Zi`、链接标志加 `/DEBUG`

即便如此，`/Ob2` 的激进内联仍会让部分栈帧失真，故仍推荐
`relwithdebinfo`。
