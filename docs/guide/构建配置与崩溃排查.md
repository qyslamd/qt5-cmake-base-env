# 构建配置与崩溃排查

## 发布约定

**发布一律使用 `relwithdebinfo` 配置**：

```bash
scripts/build_ninja.bat -t relwithdebinfo -p
```

不要用 `release` 发布。原因见下节：Release 的崩溃日志只能给出裸地址，
排查成本极高。

每次发布的 exe 与**对应的 PDB 必须一并归档**。崩溃日志与 minidump 里
记录的都是地址，事后解析要拿崩溃那一刻那个二进制匹配的 PDB。

## 各配置下的崩溃捕获能力

崩溃捕获依赖 `AddVectoredExceptionHandler` 与
`SetUnhandledExceptionFilter`，属运行时机制，`WindowsCrashHandler.cpp`
中也没有条件编译。**四个配置都能捕获崩溃**，日志与 minidump 都会写；
差别只在崩溃日志中栈回溯的**符号可读性**。

以下为实际构建并触发访问违规后的实测结果：

| 配置 | 编译标志 | 链接 `/debug` | 产出 PDB | 崩溃日志中的调用栈 |
|------|----------|:---:|:---:|--------------------|
| `debug` | `/Zi /Ob0 /Od /RTC1` | 是 | 是 | 函数名 + 文件:行 |
| `relwithdebinfo` | `/Zi /O2 /Ob1 /DNDEBUG` | 是 | 是 | 函数名 + 文件:行 |
| `release` | `/O2 /Ob2 /DNDEBUG` | 否 | 否 | `0x0091282a [未知函数]` |

`relwithdebinfo` 与 `debug` 的栈形如：

```text
 0: 0x00405019 RunCrashChild() D:\...\crashhandler_test.cpp:61
 1: 0x00409557 main()          D:\...\crashhandler_test.cpp:242
 2: 0x0046d896 __scrt_common_main_seh() ...\exe_common.inl:288
 3: 0x756a5d49 BaseThreadInitThunk()
```

`release` 的同一处形如：

```text
 0: 0x0091282a [未知函数]
 1: 0x00914f72 [未知函数]
 2: 0x0093fdcb [未知函数]
 3: 0x756a5d49 BaseThreadInitThunk()
```

Release 下系统 DLL 的帧仍能解析（它们有导出符号），只有本工程的帧因
缺少 PDB 而丢失名称。栈的帧数本身是完整的，只是没有符号。

### 帧指针省略不影响栈回溯

`/O2` 在 x86 上隐含 `/Oy`（省略帧指针），理论上会破坏 `StackWalk64`。
实测未发生：x64 的 PE 始终携带 unwind 信息；x86 在 `release` 下同样
走全了 6 帧。故该项不构成配置选择的依据。

## 符号（PDB）管理

### 归档位置

`make_package` 依赖 `make_symbols`，打包前自动把可执行文件与 PDB 复制到
带版本号与架构的目录：

```text
dist/
├── QtCMakeAppDemo-setup-x86-1.0.0.42.exe
└── symbols/
    └── 1.0.0.42-9ab3f10-x86/
        ├── demo_app.exe
        └── demo_app.pdb
```

也可单独执行归档：

```bash
cmake --build build/ninja-relwithdebinfo-x86 --target make_symbols
```

### 为什么必须归档

两个独立的原因，任何一个都足以让未归档的符号永久失效：

1. **exe 内嵌的是构建机的绝对路径**。实测
   `demo_app.exe` 中记录的 PDB 路径为
   `D:\sb\...\build\ninja-relwithdebinfo-x86\bin\demo_app.pdb`，
   分析机上该路径不存在，WinDbg **不会**自动找到符号。
2. **同一版本号可以对应不同的二进制**。版本号由 git 派生（最近的 tag 提供
   前三段、提交总数提供 build 号），工作区有未提交改动时版本号不变，但产出的
   exe 与 PDB 与干净构建不同；只按版本号归档，脏构建会覆盖掉发布构建的符号。
   故归档目录名除版本号外还带 git 短 hash。

### release 配置下的行为

`release` 不产 PDB，此时归档脚本只复制 exe 并给出告警，**不会中断打包**：

```text
CMake Warning at cmake/archive_symbols.cmake:29 (message):
  未找到符号文件（.../demo_app.pdb），本次不归档符号。
  该配置未启用调试信息，其崩溃转储将无法解析调用栈；
  发布请使用 relwithdebinfo 配置。
```

### 使用归档的符号解析转储

拿到用户的 `crash_*.dmp` 后，把符号路径指向对应的归档目录：

```text
windbg -z crash_20260911_170559.dmp

.sympath+ D:\release\symbols\1.0.0.42-9ab3f10-x86
.reload /f
!analyze -v
kb
```

`.sympath+` 追加而非覆盖，因此依然会从 Microsoft 符号服务器解析系统帧。

### 安装包不携带 PDB

`.iss` 中没有 PDB 条目，已确认安装包不会带上它。原因：单个 PDB 达
16 MB，且会暴露内部符号信息，而客户机没有解析转储的需求。符号留在
发布方一侧即可。

### 备选：符号服务器

版本多、发布频繁时，可用 `symstore.exe`（随 Windows SDK 提供）把符号
归入统一目录，或搭建符号服务器：

```bat
symstore add /r /f dist\symbols\1.0.0.42-9ab3f10-x86\*.pdb ^
    /s D:\symbols /t "demoapp" /v "1.0.0.42"
```

随后把 `.sympath` 指向 `D:\symbols` 即可，无需按版本切换路径。本项目
模板默认采用上一节的按版本目录归档，够用且无需额外工具。

## 备选：让 release 也产 PDB

若因性能原因确需用 release 发布，可为其补上调试信息：

- 在 preset 中设置
  `CMAKE_MSVC_DEBUG_INFORMATION_FORMAT:STRING=ProgramDatabase`
  （CMake 3.25+，policy CMP0141 生效时自动补 `/Zi` 与 `/DEBUG`）
- 或直接给 Release 的编译标志加 `/Zi`、链接标志加 `/DEBUG`

即便如此，`/Ob2` 的激进内联仍会让部分栈帧失真，故仍推荐
`relwithdebinfo`。
