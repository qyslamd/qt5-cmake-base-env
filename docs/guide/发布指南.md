# 发布指南

本项目的版本发布流程。Windows 产出安装程序，Linux 产出 AppImage，两条路径的
步骤一致、命令与产物格式不同。为什么必须用 `relwithdebinfo`、为什么必须归档
符号，见 [构建配置与崩溃排查](构建配置与崩溃排查.md)。

## 流程总览

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| 1 | 确认工作区干净 | 版本号不带 `-dirty` |
| 2 | 跑测试 | 测试全绿 |
| 3 | 打版本 tag 并推送 | 版本号前三段确定 |
| 4 | 构建并打包 | Windows：安装包 + 符号目录；Linux：AppImage + 符号目录 |
| 5 | 校验产物 | `dist/` 内容正确 |
| 6 | 分发 | 包给用户，符号自留 |

两侧共用同一套版本号规则与 `dist/symbols/` 目录规则，差异集中在第 2、4 步的
命令与产物格式上。

## 1. 确认工作区干净

```bash
git status --porcelain     # 应无输出
```

工作区有未提交改动时，版本号会带 `-dirty` 后缀，符号目录名也会带 —— 这是
开发构建的标记，不应作为发布产物。若确实需要发布可先提交。

## 2. 跑测试

```bash
# Windows
scripts/build_ninja.bat -t relwithdebinfo
ctest --test-dir build/ninja-relwithdebinfo-x64 --output-on-failure

# Linux
./scripts/build_ninja.sh -t relwithdebinfo
ctest --test-dir build/linux-ninja-relwithdebinfo --output-on-failure
```

Linux 侧**要用与 configure 同一份 CMake 附带的那个 `ctest`**。系统里若另有
一个旧版（Ubuntu 20.04 自带 3.16），它读不懂新版本写下的测试清单，结果是
`0 tests` 而**不是报错**——看着像"全绿"，实际一条都没跑。把该 CMake 的 `bin`
放进 `PATH` 再执行即可。

## 3. 打版本 tag

版本号的前三段取自 tag，第四段是提交总数，所以**先打 tag 再打包**。

```bash
git tag -a v1.1.0 -m "版本说明"
git push origin master
git push origin v1.1.0        # tag 不会随 master 一起推送，必须显式推
```

## 4. 构建并打包

两侧的 `-p` 都是"构建 → 打包"一条龙，且都会在打包过程中归档符号。

**Windows**：每个架构各跑一次。

```bash
scripts/build_ninja.bat -t relwithdebinfo -p            # x64（默认架构）
scripts/build_ninja.bat -a x86 -t relwithdebinfo -p     # x86
```

依次完成：构建 → 归档符号 → windeployqt → **组装 funq 工具**（`BUILD_FUNQ=ON`
时，见下）→ Inno Setup 打包。

> **`BUILD_FUNQ` 决定安装包里带不带那套 UI 自动化工具。** 开着（默认）时，
> 安装包会多一个 `funq\` 目录：位数匹配的 Python 3.8.8（用户不必自备解释器）、
> funq 的客户端与服务端包、注入库、两个启动脚本（`funq-server.bat` 起被测
> 程序并注入、`funq-self-test.bat` 驱动它走七步）、以及许可证与源码。
> 实测安装包因此从 33 MB 变成 39 MB（同时 `translations` 只带
> `qt_zh_CN.qm`，省下 3.6 MB）。发布给最终用户、且不需要现场自测能力时，
> 用 `-DBUILD_FUNQ=OFF` 打一个不带它的包。

**Linux**：只做本机架构（没有 `-a`，交叉编译不在支持范围内）。

```bash
./scripts/build_ninja.sh -t relwithdebinfo -p
```

依次完成：构建 → linuxdeploy 收集依赖 → strip 包内二进制 → appimagetool
打包 → 归档**未 strip** 的可执行文件。三个打包工具与 type2 runtime 都随仓库
提供在 `3rdparty/appimage-tools/`，全程无需联网。

## 5. 校验产物

```bash
ls dist/
```

两侧都应看到该版本的包与符号目录各一份。

## 产物说明

### Windows

以 x64 为例，实测体积：

```text
dist/
├── QtCMakeAppDemo-setup-x64-1.0.0.13.exe        39 MB   ← 分发给用户
└── symbols/
    └── 1.0.0.13-802c1a2-x64/
        ├── demo_app.exe                          1.5 MB
        └── demo_app.pdb                           16 MB  ← 自留，勿分发
```

> **上表的 exe/pdb 数字在接入图表渲染之前，含渲染载荷的那版要重量。**
> `src/markdown/markdown_res.qrc` 把两份渲染载荷编进了 exe：MathJax 1.6MB 与
> mermaid 三份 3.5MB（合计 5.1MB，纯 JS、平台无关）。代价是 `rcc` 生成的
> `qrc_markdown_res.cpp` 现在约 **14MB**（C 字面量数组，逐字节展开），编译时间
> 与 exe 体积都跟着涨；不想付这个体积的话，见 `模板使用指南.md`「按需裁剪」。
> 参考实测（x86 relwithdebinfo，未剥离符号，故偏大）：`demo_app.exe` 9.3MB、
> `qrc_markdown_res.cpp` 13.9MB。

- **安装包**：内含 exe、Qt 运行时与插件、VC++ 运行库安装程序、以及
  `funq\`（`BUILD_FUNQ=ON` 时，见上一节）；不含 PDB。安装后的目录结构：

  ```text
  {app}\
  ├── demo_app.exe、Qt5*.dll、platforms\、translations\qt_zh_CN.qm
  └── funq\                       ← BUILD_FUNQ=ON 才有，用户拿着它自测
      ├── funq-server.bat         起被测程序并注入（这个窗口要一直开着）
      ├── funq-self-test.bat      另开一个窗口跑，驱动程序走七步
      ├── python\                 随包的解释器（按架构挑的 3.8.8）
      ├── qt\                     注入库需要、主程序不需要的 Qt DLL
      ├── client\ server\         funq 的两个包 · 注入库在 server\funq_server\
      └── LICENCE*.txt source\    许可证与源码（CeCILL v2.1 是 copyleft）
  ```

  里面的路径全是相对的，装到哪台机器都成立；不再依赖用户机器上有没有 Python
- **符号目录**：目录名 = `<版本>-<git 短 hash>-<架构>`。必须与安装包一同
  留存，否则用户回传的崩溃转储无法解析

### Linux

以 x86_64 为例，实测体积：

```text
dist/
├── QtCMakeAppDemo-x86_64-1.0.0.72.AppImage      48 MB   ← 分发给用户
└── symbols/
    └── 1.0.0.72-4644fd0-x64/
        └── demo_app                              49 MB  ← 自留，勿分发
```

- **AppImage**：单文件，`chmod +x` 后直接运行；内含 Qt 运行库与插件，
  包内可执行文件已被 strip（`file` 报 `stripped`，与之对照，符号目录里那份报
  `with debug_info, not stripped`）
- **符号目录**：目录名同样是 `<版本>-<git 短 hash>-<架构>`，但**架构写法与
  包名不同**——符号目录用 `x64`，AppImage 文件名用 `x86_64`（前者是
  `APP_ARCH_SUFFIX`，后者是 `APPIMAGE_ARCH`）。脚本里不要拿其中一个去匹配
  另一个
- 归档的是**未 strip 的可执行文件本身**（Linux 没有独立的符号文件），所以它
  同时也能直接运行——别把它当成"只是符号"而随手删掉

## 版本号规则

```text
1.0.0.13
│ │ │ └── build 号：提交总数（git rev-list --count HEAD）
│ │ └──── patch ┐
│ └────── minor ├── 最近的 v1.2.3 形式 tag
└──────── major ┘
```

未打 tag 时前三段为 `0.0.0`。exe 的版本资源中还记录了 git 短 hash
（`GitCommit` 字段），从文件属性即可看出它对应哪次提交。

## 常见问题

**在 Debug 配置下打包被拒绝**
这是刻意拦截的，两侧理由不同：

- Windows：Debug 使用调试版 C 运行时（`/MDd`），产物依赖
  `ucrtbased.dll`、`vcruntime140.dll`、`msvcp140.dll` 等 —— 这些**不在
  VC++ 可再发行包内**，安装到用户机器上必然启动失败；而开发机装有 Visual
  Studio，本地根本测不出这个问题。拦截发生在 ISCC 之前，不会产出安装包。
- Linux：没有运行时缺失的问题，拒绝的理由是产物体积大、带断言开销，而
  AppImage 反正要把调试信息 strip 掉——发布出去既没有性能优势，也没有可解析
  的符号。

非 `relwithdebinfo` 的其它配置（如 `release`）两侧都只告警不拦截，因为它们的
产物能正常运行，只是丢失可解析的调试符号。

**tag 推上去了但远程没有**
`git push` 默认不推送 tag，须显式执行 `git push origin v1.1.0`。
可用 `git ls-remote --tags origin` 确认。

**CI 上版本号不对**
浅克隆（`--depth=1`）下 `git rev-list --count` 只数到克隆深度，build 号
偏小。需要 `fetch-depth: 0`，或先执行 `git fetch --unshallow`。

**版本号带 `-dirty`**
工作区有未提交改动（含未跟踪文件之外的一切改动）。提交后再构建即可消除。

**两个架构的安装包会互相覆盖吗**
（Windows）不会。Inno Setup 的 AppId 按架构分开（`APPINSTALLER_ID_X64` /
`_X86`），可同机共存。

**Linux 上打包卡在 `Downloading runtime file from ...`**
`appimagetool` 产出 AppImage 前要嵌入一份 type2 runtime，若没显式给
`--runtime-file` 它会去 GitHub 的 release CDN 拉，而那个下载**没有超时**：
进程 CPU 为 0、看着像卡在压缩，实为干等。本仓库已把 runtime 与三个工具一并
入库，`make_appimage.sh` 显式指过去；缺文件时会被前置检查直接拦下并说明。

**在容器 / 无 FUSE 的环境里打包或运行 AppImage 失败**
脚本已导出 `APPIMAGE_EXTRACT_AND_RUN`，让工具免 FUSE 自解包运行。

**configure 阶段有 WARNING**
那是模板防呆提示，说明 `PROJECT_NAME_STR` 或安装包 GUID 仍是模板默认值。
新建项目按 `模板使用指南.md` 的必改项处理后即消失。

**没有 git 环境（如导出的源码包）**
版本号回落 `0.0.0.0` 并给出告警。需要固定版本号时显式指定：

```bash
cmake -S . -B build/xxx -DAPP_VERSION_OVERRIDE=1.2.3.4
```
