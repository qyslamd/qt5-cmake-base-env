# 发布指南

本项目的版本发布流程。为什么必须用 `relwithdebinfo`、为什么必须归档符号，
见 [构建配置与崩溃排查](构建配置与崩溃排查.md)。

## 流程总览

| 步骤 | 做什么 | 产出 |
|------|--------|------|
| 1 | 确认工作区干净 | 版本号不带 `-dirty` |
| 2 | 跑测试 | 测试全绿 |
| 3 | 打版本 tag 并推送 | 版本号前三段确定 |
| 4 | 逐架构构建并打包 | 安装包 + 符号目录 |
| 5 | 校验产物 | `dist/` 内容正确 |
| 6 | 分发 | 安装包给用户，符号自留 |

## 1. 确认工作区干净

```bash
git status --porcelain     # 应无输出
```

工作区有未提交改动时，版本号会带 `-dirty` 后缀，符号目录名也会带 —— 这是
开发构建的标记，不应作为发布产物。若确实需要发布可先提交。

## 2. 跑测试

```bash
scripts/build_ninja.bat -t relwithdebinfo
ctest --test-dir build/ninja-relwithdebinfo-x64 --output-on-failure
```

## 3. 打版本 tag

版本号的前三段取自 tag，第四段是提交总数，所以**先打 tag 再打包**。

```bash
git tag -a v1.1.0 -m "版本说明"
git push origin master
git push origin v1.1.0        # tag 不会随 master 一起推送，必须显式推
```

## 4. 构建并打包

每个架构各跑一次。`-p` 会依次完成：构建 → 归档符号 → windeployqt →
Inno Setup 打包。

```bash
scripts/build_ninja.bat -t relwithdebinfo -p            # x64（默认架构）
scripts/build_ninja.bat -a x86 -t relwithdebinfo -p     # x86
```

## 5. 校验产物

```bash
ls dist/
```

应当看到该版本的安装包与符号目录各一份。

## 产物说明

以 x64 为例，实测体积：

```text
dist/
├── QtCMakeAppDemo-setup-x64-1.0.0.13.exe        33 MB   ← 分发给用户
└── symbols/
    └── 1.0.0.13-802c1a2-x64/
        ├── demo_app.exe                          1.5 MB
        └── demo_app.pdb                           16 MB  ← 自留，勿分发
```

- **安装包**：内含 exe、Qt 运行时与插件、VC++ 运行库安装程序；不含 PDB
- **符号目录**：目录名 = `<版本>-<git 短 hash>-<架构>`。必须与安装包一同
  留存，否则用户回传的崩溃转储无法解析

## 版本号规则

```text
1.0.0.13
│ │ │ └── build 号：提交总数（git rev-list --count HEAD）
│ │ └──── patch ┐
│ └────── minor ├── 最近的 v1.2.3 形式 tag
└──────── major ┘
```

未打 tag 时前三段为 `0.0.0`。exe 的版本资源中还记录了 git 短 hash
（`GitCommit` 字段），从文件属性即可看出它对应哪次提交。

## 常见问题

**在 Debug 配置下打包被拒绝**
这是刻意拦截的。Debug 使用调试版 C 运行时（`/MDd`），产物依赖
`ucrtbased.dll`、`vcruntime140d.dll`、`msvcp140d.dll` 等 —— 这些**不在
VC++ 可再发行包内**，安装到用户机器上必然启动失败；而开发机装有 Visual
Studio，本地根本测不出这个问题。拦截发生在 ISCC 之前，不会产出安装包。

非 `relwithdebinfo` 的其它配置（如 `release`）只告警不拦截，因为它们的产物
能正常运行，只是丢失调试符号。

**tag 推上去了但远程没有**
`git push` 默认不推送 tag，须显式执行 `git push origin v1.1.0`。
可用 `git ls-remote --tags origin` 确认。

**CI 上版本号不对**
浅克隆（`--depth=1`）下 `git rev-list --count` 只数到克隆深度，build 号
偏小。需要 `fetch-depth: 0`，或先执行 `git fetch --unshallow`。

**版本号带 `-dirty`**
工作区有未提交改动（含未跟踪文件之外的一切改动）。提交后再构建即可消除。

**两个架构的安装包会互相覆盖吗**
不会。Inno Setup 的 AppId 按架构分开（`APP_INSTALLER_ID_X64` /
`_X86`），可同机共存。

**configure 阶段有 WARNING**
那是模板防呆提示，说明 `PROJECT_NAME_STR` 或安装包 GUID 仍是模板默认值。
新建项目按 `模板使用指南.md` 的必改项处理后即消失。

**没有 git 环境（如导出的源码包）**
版本号回落 `0.0.0.0` 并给出告警。需要固定版本号时显式指定：

```bash
cmake -S . -B build/xxx -DAPP_VERSION_OVERRIDE=1.2.3.4
```
